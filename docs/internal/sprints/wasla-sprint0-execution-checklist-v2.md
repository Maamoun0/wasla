# ⚙️ وصلة (Wasla) — دليل تنفيذ السبرنت 0 (نسخة محسَّنة)
### عقد موحَّد لكل مهمة ذرية — تحل محل النسخة السابقة بالكامل

> **لماذا نسخة جديدة؟** النسخة السابقة كانت مفيدة لكن غير متّسقة: ترتيب منطقي ناقص (CI في الآخر بدل الأول)، فحص أمني للأسرار مؤجَّل بدل فوري، مهام لسه مجمَّعة أكبر من اللازم، ومفيش بنية ثابتة توضح بالضبط حدود كل مهمة ودليل النجاح المطلوب. هذه النسخة تصحح الأربعة.

---

## 📐 العقد الموحَّد لكل مهمة ذرية (Template)

كل مهمة أدناه تتبع **نفس البنية بالضبط**، بلا استثناء:

```
🔹 النوع:           [كود / إعداد يدوي / بحث]
🔹 المدخلات:         [ما الذي يحتاج الوكيل الاطلاع عليه قبل البدء]
🔹 داخل النطاق:      [بالضبط ما يُسمح له بلمسه]
🔹 خارج النطاق:      [صراحة ما يُمنع عليه لمسه، ولو بدا مرتبطاً]
🔹 المُخرَج المطلوب:  [الملفات/الحالة المتوقعة بنهاية المهمة]
🔹 دليل الإثبات:     [ما الذي يجب أن يُرسله الوكيل لك حرفياً كدليل، لا وصفاً]
🔹 فحصك المباشر:     [خطوة تتحقق منها بنفسك من المصدر، لا من كلام الوكيل]
🔹 عند الفشل:        [ماذا تفعل تحديداً لو فشل الفحص]
```

**لماذا هذا التشدد؟** لأن أسلوب عملك (تنفيذ بوكيل + مقارنة + اختيار الأفضل) يحتاج مهام **ذرية بما يكفي** بحيث لو شغّلت نفس المهمة بوكيلين مختلفين، الفرق بينهما يكون في جودة التنفيذ نفسه، لا في اختلاف فهم كل وكيل لحدود المهمة من الأساس.

## 🧩 القطعة 1 — إعداد البيئات (يدوي بالكامل)

### 1.1 إنشاء مشروع Supabase Staging
```
🔹 النوع: إعداد يدوي
🔹 المدخلات: لا شيء — بداية نظيفة
🔹 داخل النطاق: إنشاء مشروع باسم wasla-staging فقط
🔹 خارج النطاق: عدم تشغيل أي SQL أو ربط أي مفتاح بأي مكان بعد
🔹 المُخرَج المطلوب: Project URL + anon key + service_role key محفوظون محلياً (password manager، لا ملف نصي عادي)
🔹 دليل الإثبات: لا ينطبق (مهمة يدوية، التحقق مباشر)
🔹 فحصك المباشر: تسجيل دخول للوحة Supabase، رؤية المشروع، نسخ المفاتيح فعلياً
🔹 عند الفشل: لا ينطبق — خطوة بسيطة بلا تعقيد فني
```

### 1.2 إنشاء مشروع Supabase Production (فارغ)
```
🔹 النوع: إعداد يدوي
🔹 داخل النطاق: إنشاء مشروع باسم wasla-production فقط
🔹 خارج النطاق: ⚠️ صفر SQL، صفر بيانات، صفر اختبار على هذا المشروع حتى السبرنت 10
🔹 فحصك المباشر: مقارنة Project URL بين Staging وProduction — يجب أن يكونا مختلفين تماماً بصرياً
```

### 1.3 مستودع Git + الحماية من تسريب الأسرار من أول لحظة
```
🔹 النوع: إعداد يدوي
🔹 داخل النطاق: إنشاء مستودع خاص (Private) على GitHub
🔹 المُخرَج المطلوب: أول Commit يحتوي .gitignore فقط، يستثني: .env, .env.*, *.keystore, *.jks, /build/, .dart_tool/, google-services.json, GoogleService-Info.plist
🔹 فحصك المباشر: فتح الملف على GitHub مباشرة بعد الرفع والتأكد بصرياً من محتواه الكامل
🔹 عند الفشل: لا تُكمِل لأي خطوة تالية حتى هذا الملف صحيح 100% — هذا أهم سطر دفاع في كل المشروع
```

### 1.4 فروع Git الأساسية
```
🔹 داخل النطاق: إنشاء فرعي main وdevelop من نفس نقطة البداية
🔹 فحصك المباشر: صفحة Branches على GitHub تُظهر الفرعين بالاسم الصحيح بالضبط
```

## 🧩 القطعة 2 — خط CI الأساسي **(انتقلت هنا، قبل أي كود فيتشر، بقرار مُصحَّح)**

### 2.1 إعداد GitHub Actions: analyze + test
```
🔹 النوع: كود
🔹 المدخلات: مشروع Flutter فارغ أو بهيكله الحالي (قبل أي تعديل من المراحل السابقة)
🔹 داخل النطاق: ملف .github/workflows/ci.yml يُشغِّل flutter analyze وflutter test تلقائياً عند أي Pull Request نحو develop
🔹 خارج النطاق: لا نشر، لا بناء APK/IPA في هذه الخطوة — تحقق فقط
🔹 المُخرَج المطلوب: ملف workflow واحد فقط
🔹 دليل الإثبات: رابط مباشر لتشغيل الـ Action على GitHub بعد أول Pull Request تجريبي
🔹 فحصك المباشر: فتح الرابط ورؤية ✅ أخضر فعلياً، لا الاكتفاء بتقرير الوكيل
🔹 عند الفشل: لا تنتقل لأي مهمة كود لاحقة — كل الكود القادم يعتمد على هذا الخط لاكتشاف الانحدار مبكراً
```

### 2.2 إضافة فحص أساسي لتسريب الأسرار (Secret Scanning) — **مهمة جديدة لم تكن موجودة، أُضيفت بقرار مُصحَّح**
```
🔹 النوع: كود
🔹 المدخلات: ملف ci.yml من الخطوة السابقة
🔹 داخل النطاق: إضافة خطوة في نفس الـ workflow تستخدم أداة مجانية بسيطة (مثل gitleaks) تفحص أي مفتاح/سر يبدو مكشوفاً في الكود المُرسَل بكل Pull Request
🔹 خارج النطاق: لا إعداد متقدم أو قواعد مخصصة الآن — الإعداد الافتراضي للأداة كافٍ في هذه المرحلة
🔹 المُخرَج المطلوب: خطوة إضافية في ci.yml، تفشل الـ Action إن وُجد أي سر مكشوف
🔹 دليل الإثبات: تجربة عمدية — إضافة سطر فيه مفتاح وهمي شكله حقيقي في فرع تجريبي، ورؤية الـ Action يفشل فعلاً، ثم حذف السطر
🔹 فحصك المباشر: رؤية الفشل المتعمَّد بعينك، لا تصديق أن الأداة "مفعَّلة" بدون تجربة فعلية تُثبت ذلك
🔹 عند الفشل: إن لم تكتشف الأداة المفتاح الوهمي، الإعداد غير صحيح ويُعاد قبل أي خطوة تالية
```

## 🧩 القطعة 3 — SQL المرحلة 0

### 3.1 مراجعة التعارضات (بحث، لا كتابة كود بعد)
```
🔹 النوع: بحث
🔹 المدخلات: wasla-phase0-schema-additions.sql + wasla-schema.sql الأصلي (34 جدول)
🔹 داخل النطاق: تحديد فقط — هل يوجد جدول "مناطق" بنفس غرض districts؟ أي تعارض أسماء آخر محتمل؟
🔹 خارج النطاق: لا تعديل على أي ملف SQL في هذه الخطوة، تقرير فقط
🔹 المُخرَج المطلوب: قائمة نصية بكل تعارض مكتشَف (أو تأكيد صريح "لا يوجد تعارض")
🔹 دليل الإثبات: اقتباس مباشر (لا إعادة صياغة) للأسطر المتعارضة من كلا الملفين جنباً إلى جنب
🔹 فحصك المباشر: قراءتك الشخصية للأسطر المُقتبَسة، لا ملخص الوكيل عنها
```

### 3.2 تعديل SQL بناءً على نتيجة المراجعة (فقط إن وُجد تعارض)
```
🔹 النوع: كود
🔹 المدخلات: تقرير الخطوة 3.1
🔹 داخل النطاق: تعديل القسم المتعارض فقط من wasla-phase0-schema-additions.sql
🔹 خارج النطاق: عدم لمس أي قسم آخر من الملف لم يُذكَر في التقرير
🔹 المُخرَج المطلوب: نسخة مُحدَّثة من الملف + توضيح دقيق لكل سطر تغيّر
```

### 3.3 اختبار قابلية إعادة التشغيل الآمنة (Idempotency) — **مهمة جديدة، غير موجودة سابقاً**
```
🔹 النوع: كود
🔹 المدخلات: نسخة SQL النهائية (بعد 3.1/3.2)
🔹 داخل النطاق: تأكيد أن كل أمر CREATE في الملف يستخدم IF NOT EXISTS حيثما أمكن (موجود جزئياً بالفعل في النسخة الأصلية)، وأن تشغيل الملف مرتين متتاليتين على قاعدة بيانات تجريبية فارغة لا يُنتج خطأ يوقف التنفيذ في المرة الثانية
🔹 المُخرَج المطلوب: تقرير "نعم، الملف آمن لإعادة التشغيل" أو قائمة بالأوامر التي تحتاج تعديلاً
🔹 دليل الإثبات: نص ناتج التنفيذ الفعلي للمحاولة الثانية، كاملاً دون تلخيص
🔹 فحصك المباشر: قراءة الناتج بنفسك، التأكد أن لا توجد رسالة خطأ توقف تنفيذ بقية الملف
🔹 عند الفشل: تصحيح الأوامر المتعارضة قبل أي تشغيل فعلي على Staging الحقيقي
```

### 3.4 التشغيل الفعلي على Staging
```
🔹 النوع: كود (تنفيذ مباشر)
🔹 داخل النطاق: تشغيل الملف المُختبَر (من 3.3) على wasla-staging حصراً
🔹 خارج النطاق: ⚠️ ممنوع التشغيل على wasla-production نهائياً في هذا السبرنت
🔹 المُخرَج المطلوب: كل الجداول/الأعمدة الجديدة موجودة فعلياً على Staging
🔹 دليل الإثبات: لقطة شاشة أو نص استعلام \dt من لوحة Supabase يُظهر الجداول الجديدة
🔹 فحصك المباشر (من لوحة Supabase مباشرة، لا تقرير الوكيل):
   ☐ جدول device_tokens موجود
   ☐ جدول otp_requests موجود، صفر RLS Policy تسمح بوصول العميل (تحقق من تبويب Policies مباشرة)
   ☐ ai_risk_level وai_review_notes في جدول ads
   ☐ deleted_at في users وads وreviews
   ☐ legal_acceptances وaccount_deletion_requests موجودان
```

## 🧩 القطعة 4 — حماية OTP (مُقسَّمة أدق من النسخة السابقة)

### 4.1 بناء Edge Function `request-otp` فقط (Backend بحت)
```
🔹 النوع: كود
🔹 المدخلات: المواصفة الكاملة من موجز "المهمة أ" السابق (3/10 دقائق، 10/يوم)
🔹 داخل النطاق: ملف Edge Function واحد فقط، نشره على Staging
🔹 خارج النطاق: ⚠️ صفر تعديل على أي ملف Dart في هذه الخطوة
🔹 المُخرَج المطلوب: endpoint فعّال يستقبل phone_number ويُرجِع نجاح أو RATE_LIMIT_SHORT/RATE_LIMIT_DAILY
🔹 دليل الإثبات: نص 4 استدعاءات فعلية متتالية (عبر curl/Postman) بنفس الرقم، مع الناتج الكامل لكل استدعاء
🔹 فحصك المباشر: قراءة الناتج الرابع بنفسك، التأكد أنه فعلاً RATE_LIMIT_SHORT لا نجاح
🔹 عند الفشل: لا تنتقل لربط Flutter أبداً قبل أن تنجح هذه الخطوة بمعزل تام
```

### 4.2 تعديل Auth Screen فقط (الإرسال الأول)
```
🔹 النوع: كود
🔹 المدخلات: نتيجة 4.1 الناجحة
🔹 داخل النطاق: ملف Auth Screen فقط — استبدال استدعاء OTP المباشر بـ request-otp
🔹 خارج النطاق: ⚠️ عدم لمس OTP Screen (زر إعادة الإرسال) في هذه الخطوة — مهمة منفصلة تالية
🔹 المُخرَج المطلوب: شاشة Auth تستدعي الـ Edge Function الجديدة فقط
🔹 دليل الإثبات: نتيجة بحث نصي عن "signInWithOtp" داخل ملف هذه الشاشة تحديداً → صفر نتائج
🔹 فحصك المباشر: تجربة فعلية على المحاكي — طلب OTP أول مرة يصل الكود فعلاً
```

### 4.3 تعديل OTP Screen فقط (زر إعادة الإرسال)
```
🔹 النوع: كود
🔹 داخل النطاق: ملف OTP Screen فقط — زر "إعادة الإرسال" يستدعي request-otp أيضاً
🔹 خارج النطاق: عدم لمس Auth Screen مجدداً (انتهت في 4.2)
🔹 دليل الإثبات: نفس فحص البحث النصي، مطبَّق على ملف OTP Screen تحديداً
🔹 فحصك المباشر: الضغط على "إعادة الإرسال" 4 مرات سريعة فعلياً على المحاكي → رسالة عربية واضحة بصوت العلامة تظهر، لا خطأ تقني خام
🔹 عند الفشل: تحقق أولاً إن كانت الرسالة تصل من الـ Edge Function نفسها بشكل صحيح (مهمة 4.1) قبل افتراض أن المشكلة في الواجهة
```

### 4.4 اختبار الانحدار الكامل
```
🔹 النوع: كود (تشغيل أوامر فقط)
🔹 داخل النطاق: تشغيل flutter test وflutter analyze على المشروع كاملاً
🔹 المُخرَج المطلوب: صفر تحذيرات جديدة، صفر اختبارات فاشلة
🔹 دليل الإثبات: الناتج الكامل للأمرين، دون تلخيص أو اقتطاع
🔹 فحصك المباشر: قراءة الناتج بنفسك سطراً سطراً إن كان قصيراً، أو البحث عن كلمة "FAIL"/"error" تحديداً إن كان طويلاً
```

## ✅ ما تغيَّر فعلياً عن النسخة السابقة (للمقارنة المباشرة)

```
🔄 CI انتقل ليكون أول قطعة فعلية بعد إعداد البيئات، لا آخر قطعة
🆕 فحص تسريب الأسرار (Secret Scanning) أُضيف من اليوم الأول، لا أُجِّل
🆕 اختبار قابلية إعادة تشغيل SQL بأمان (Idempotency) أُضيف كخطوة مستقلة قبل التشغيل الفعلي
🔄 مهمة "ربط Flutter" (كانت خطوة واحدة) انقسمت لخطوتين منفصلتين: Auth Screen ثم OTP Screen
🆕 كل مهمة الآن بعقد ثابت: نوع، مدخلات، نطاق داخل/خارج، مُخرَج، دليل إثبات، فحصك المباشر، خطة عند الفشل
```

هذه النسخة هي المرجع الفعلي للسبرنت 0 الآن — تجاهل النسخة السابقة بالكامل عند الإرسال للوكيل.
