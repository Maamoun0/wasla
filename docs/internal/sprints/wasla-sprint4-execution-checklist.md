## 🧩 القطعة 1 — Supabase Storage: Bucket وثائق الهوية (قبل أي كود Flutter)

### 1.1 إنشاء bucket `id-documents` بإعدادات أمنية صحيحة
```
🔹 النوع: إعداد يدوي من لوحة Supabase
🔹 المدخلات: قسم 2.1 من خطة أمن وحماية البيانات
🔹 داخل النطاق: إنشاء bucket اسمه id-documents، مضبوط Private صراحة من إعدادات Storage
🔹 خارج النطاق: ⚠️ لا تُضاف أي RLS Policy تسمح بوصول العميل مباشرة — الوصول فقط عبر Service Role من Edge Function
🔹 فحصك المباشر: محاولة فتح أي رابط مباشر لملف داخل الـ bucket بدون Signed URL → يجب أن تحصل على رفض (403/401)، لا ملف مفتوح. هذا الفحص لا يُفوَّض للوكيل
```

### 1.2 دالة توليد Signed URL مؤقت (5 دقائق فقط)
```
🔹 النوع: كود (Edge Function مساعدة أو دالة في لوحة الإدارة لاحقاً)
🔹 داخل النطاق: دالة تستدعى بصلاحية Service Role فقط، تُنتج Signed URL صالحاً لـ5 دقائق فقط
🔹 خارج النطاق: هذه الدالة لا تُستدعى من تطبيق Flutter بأي شكل — فقط من لوحة الإدارة (مرحلة 12)
🔹 دليل الإثبات: Signed URL تجريبي + التأكد أنه يرفض الوصول بعد انتهاء المدة (اختبار بعد 5 دقائق فعلاً)
🔹 فحصك المباشر: انتظار 6 دقائق بعد توليد الرابط ومحاولة فتحه → يجب أن تحصل على رفض
```

### 1.3 Audit Log — سجل كل وصول لوثيقة هوية
```
🔹 النوع: كود
🔹 المدخلات: قسم 2.2 من خطة الأمن — كل فتح Signed URL يُسجَّل في جدول audit_log
🔹 داخل النطاق: إنشاء جدول audit_log (إن لم يكن موجوداً بالفعل في wasla-schema.sql) + إدراج صف في كل مرة تُولَّد فيها Signed URL
🔹 فحصك المباشر: توليد Signed URL مرتين → فحص جدول audit_log يدوياً يُظهر صفّين فعلاً
```

## 🧩 القطعة 2 — Verification Screen

### 2.1 التحقق المحلي من صيغة الرقم القومي (بدون شبكة)
```
🔹 النوع: كود
🔹 المدخلات: قواعد التحقق من موجز مرحلة 10: 14 رقماً، أول رقم 2 أو 3، الأرقام 2-7 تاريخ صحيح
🔹 داخل النطاق: دالة تحقق محلية بحتة (لا استدعاء شبكة)
🔹 خارج النطاق: صفر استدعاء شبكة في هذه الدالة مهما كان السبب
🔹 المُخرَج المطلوب: دالة validateNationalId(String id) → تُرجِع bool + رسالة خطأ محددة
🔹 دليل الإثبات: Unit Tests تغطي بالضبط:
   - 13 رقماً → رفض
   - 15 رقماً → رفض
   - أول رقم 1 → رفض
   - أول رقم 4 → رفض
   - تاريخ مستحيل (شهر 13) → رفض
   - رقم قومي صحيح حقيقي الصيغة → قبول
🔹 فحصك المباشر: قراءة كل اختبار بنفسك والتأكد أنه يغطي الحالة المذكورة تحديداً، لا حالة مختلفة بنفس الاسم
🔹 عند الفشل: لا تنتقل لربط النموذج بالواجهة قبل نجاح كل الاختبارات الستة
```

### 2.2 نموذج الإدخال (كاميرا فقط، لا معرض)
```
🔹 النوع: كود
🔹 المدخلات: القرار الأمني من موجز مرحلة 10: ImageSource.camera فقط، تعطيل gallery صراحة
🔹 داخل النطاق: حقلا الاسم الكامل والرقم القومي + زر تصوير وجه البطاقة + زر تصوير ظهر البطاقة
🔹 خارج النطاق: صفر رفع لـ Supabase Storage في هذه الخطوة — تصوير وتخزين محلي مؤقت فقط
🔹 فحصك المباشر: الضغط على "اختيار من الصور" (إن ظهر أصلاً) → يجب ألا يوجد هذا الخيار من الأساس، لا أن يكون موجوداً لكن معطَّلاً
```

### 2.3 Edge Function `submit-kyc-request`
```
🔹 النوع: كود
🔹 داخل النطاق: رفع الصورتين لـ bucket id-documents (بمسار {user_id}/kyc/{timestamp}/) + إدراج صف في جدول طلبات التحقق بحالة pending + التحقق من عدم وجود طلب pending نشط قبل القبول
🔹 خارج النطاق: ⚠️ الرفع يتم من Edge Function بصلاحية Service Role، لا مباشرة من Flutter لضمان مسار التخزين الصحيح والأمان
🔹 دليل الإثبات: طلب تجريبي ناجح + فحص bucket مباشرة في لوحة Supabase والتأكد أن الملفات في المسار الصحيح وغير مرئية بدون Signed URL
🔹 فحصك المباشر:
   ☐ الملفان في bucket id-documents في المسار الصحيح
   ☐ صف جديد في جدول طلبات التحقق بحالة pending
   ☐ محاولة إرسال طلب ثانٍ فوراً → مرفوض بوضوح لوجود طلب pending نشط
```

### 2.4 عرض حالة الطلب للمستخدم
```
🔹 النوع: كود
🔹 داخل النطاق: ثلاث حالات واضحة بصرياً ونصياً: pending (مع تقدير زمني 24-48 ساعة)، مقبول (يُظهر badge موثّق فوراً)، مرفوض (مع سبب من القائمة الموحَّدة + زر إعادة المحاولة)
🔹 دليل الإثبات: تغيير حالة الطلب يدوياً من لوحة Supabase وتحديث الشاشة للتأكد من ظهور كل حالة بشكلها الصحيح
🔹 فحصك المباشر: اختبار الحالات الثلاث يدوياً بتعديل مباشر في قاعدة البيانات، لا انتظار مراجعة بشرية فعلية
```

## 🧩 القطعة 3 — My Reviews Screen

### 3.1 جلب التقييمات (تبويبان منفصلان)
```
🔹 النوع: كود
🔹 داخل النطاق: استعلامان منفصلان للتبويبين (واردة/صادرة) + Pagination بحجم 20 تقييماً
🔹 خارج النطاق: لا تحميل كل التقييمات دفعة واحدة مهما كان عددها صغيراً في الاختبار — الـ Pagination إلزامي من اليوم الأول
🔹 دليل الإثبات: استعلام مباشر على قاعدة البيانات يُثبت أن كل صفحة تجلب 20 صفاً فقط لا أكثر
🔹 فحصك المباشر: إضافة 25 تقييماً تجريبياً مباشرة في قاعدة البيانات، والتأكد أن الشاشة تعرض 20 فقط في البداية ثم تحمّل الـ5 الباقية عند التمرير
```

### 3.2 منطق الرد (مرة واحدة، لا تعديل)
```
🔹 النوع: كود
🔹 المدخلات: القرار من موجز مرحلة 10: رد واحد فقط، لا تعديل، لا حذف
🔹 داخل النطاق: زر "رد" يظهر فقط لتقييم بلا رد مسبق، يختفي فور الإرسال الناجح
🔹 دليل الإثبات: إرسال رد تجريبي → اختفاء الزر فوراً + التأكد بفحص قاعدة البيانات أن الرد مسجَّل
🔹 فحصك المباشر: محاولة إرسال ردّين على نفس التقييم (عبر API مباشرة) → يجب أن يُرفَض الثاني من جانب الخادم، لا فقط من الواجهة
```

### 3.3 حالة الفراغ (Empty State)
```
🔹 النوع: كود
🔹 داخل النطاق: رسالة ودودة ومحفِّزة لكل تبويب فارغ (لا شاشة فارغة بلا محتوى)
🔹 فحصك المباشر: حساب تجريبي جديد بصفر تقييمات → رؤية العنصر النائب بنفسك
```

## 🧩 القطعة 4 — صيغة trust_score ومكوّن TrustBadge

### 4.1 تحديث Function الـ trust_score في قاعدة البيانات
```
🔹 النوع: كود
🔹 المدخلات: الصيغة المُعتمَدة من موجز مرحلة 10:
   - التوثيق: 30 نقطة (30 إذا موثّق، 0 غير ذلك)
   - متوسط التقييمات: (متوسط النجوم ÷ 5) × 40
   - عدد التقييمات: نقطة لكل تقييم، حد أقصى 20
   - عمر الحساب: نقطة لكل شهر، حد أقصى 10
🔹 داخل النطاق: تحديث الـ Function الموجودة فعلاً (من المرحلة 5 الأصلية) لتطبّق هذه الصيغة تحديداً
🔹 خارج النطاق: لا إنشاء Function جديدة إن كانت موجودة — تعديل على الموجود فقط لتفادي تعارض Triggers
🔹 دليل الإثبات: Unit Test للصيغة الحسابية يغطي 4 حالات:
   - مستخدم موثّق + 20 تقييم بمتوسط 5 نجوم + حساب عمره 10 أشهر → 100 نقطة
   - مستخدم غير موثّق + 10 تقييمات بمتوسط 4 نجوم + حساب عمره 5 أشهر → 47 نقطة (0+32+10+5)
   - مستخدم موثّق + 0 تقييمات + حساب جديد → 30 نقطة
   - مستخدم غير موثّق + 0 تقييمات + حساب جديد → 0 نقطة
🔹 فحصك المباشر: احسب النتائج الأربعة بنفسك على الورق أو آلة حاسبة، قارنها بنتائج الاختبار
```

### 4.2 تشغيل الـ Function تلقائياً بعد كل تقييم جديد
```
🔹 النوع: كود
🔹 داخل النطاق: التأكد أن Trigger الموجود فعلاً يستدعي الـ Function المُحدَّثة، لا النسخة القديمة
🔹 دليل الإثبات: إدراج تقييم تجريبي مباشرة في قاعدة البيانات + قراءة trust_score للمستخدم بعد ثوانٍ للتأكد من التحديث التلقائي
🔹 فحصك المباشر: قراءة القيمة قبل التقييم وبعده مباشرة من لوحة Supabase
```

### 4.3 مكوّن TrustBadge الموحَّد
```
🔹 النوع: كود
🔹 المدخلات: شرائح العرض المُعتمَدة: 0-39 رمادي "جديد"، 40-69 فيروزي "موثوق"، 70-100 ذهبي "موثّق بدرجة عالية" + علامة صح منفصلة لـ is_verified
🔹 داخل النطاق: Widget واحد يستقبل (trustScore, isVerified) فقط
🔹 خارج النطاق: ⚠️ لا نسخ متعددة لنفس المكوّن في أماكن مختلفة — مكوّن واحد يُستورَد في كل مكان
🔹 دليل الإثبات: بحث نصي في كل ملفات المشروع لأي تطبيق trust badge خارج هذا المكوّن الواحد → صفر نتائج
🔹 فحصك المباشر: فتح 4 شاشات مختلفة تعرض الـ TrustBadge (بطاقة إعلان، تفاصيل إعلان، ملف شخصي، ملف معلن عام) والتأكد بصرياً أنها متطابقة تماماً في الشكل
```
