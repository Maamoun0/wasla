## 🧩 القطعة 1 — حساب Paymob Sandbox (تحضير قبل أي كود)

### 1.1 إعداد حساب Paymob Sandbox وحفظ المفاتيح
```
🔹 النوع: إعداد يدوي
🔹 داخل النطاق: إنشاء حساب Paymob على بيئة Sandbox، الحصول على: API Key، HMAC Secret، Integration ID للبطاقات
🔹 خارج النطاق: ⚠️ مفاتيح Live (الإنتاج الحقيقي) لا تُلمَس ولا تُنشَأ حتى السبرنت 10
🔹 فحصك المباشر: حفظ المفاتيح في Supabase Secrets على Staging فقط، وتأكيد أنها غير موجودة في أي ملف Dart أو في تاريخ Git عبر بحث نصي
```

### 1.2 مراجعة وثائق Paymob Sandbox — ترتيب حقول HMAC
```
🔹 النوع: بحث
🔹 المدخلات: وثائق Paymob الرسمية
🔹 داخل النطاق: توثيق **الترتيب الدقيق للحقول** المستخدَمة في حساب توقيع HMAC الخاص بـ Paymob تحديداً (هذا الترتيب سيُستخدَم في السبرنت 6 ببناء payment-webhook)
🔹 المُخرَج المطلوب: قائمة مرتبة بأسماء الحقول بالضبط كما هي في وثائق Paymob، محفوظة كمرجع للسبرنت القادم
🔹 لماذا الآن؟ لأن الاستعجال في كتابة منطق HMAC بدون هذا المرجع هو المصدر الأشهر لفشل التكامل مع Paymob بصمت
```

## 🧩 القطعة 2 — Boost Ad Screen

### 2.1 جلب باقات Boost من قاعدة البيانات
```
🔹 النوع: كود
🔹 المدخلات: جدول boost_packages (تحقق من اسمه الفعلي في wasla-schema.sql الأصلي)
🔹 داخل النطاق: استعلام يجلب الباقات مرتبة بالسعر + عرضها في واجهة اختيار واضحة
🔹 خارج النطاق: ⚠️ لا تُثبَّت الباقات أو الأسعار في كود Dart — من قاعدة البيانات فقط
🔹 دليل الإثبات: تعديل سعر باقة مباشرة من لوحة Supabase → التأكد أن الشاشة تعرض السعر الجديد بعد تحديثها بدون أي تغيير في الكود
🔹 فحصك المباشر: تجربة التعديل المذكور بنفسك
```

### 2.2 قائمة الإعلانات القابلة للتعزيز
```
🔹 النوع: كود
🔹 المدخلات: شرط مزدوج: status = 'active' AND (boost_expires_at IS NULL OR boost_expires_at < now())
🔹 داخل النطاق: استعلام مفلتَر + عرض القائمة
🔹 خارج النطاق: إعلانات بحالة pending/expired/rejected لا تظهر في القائمة مطلقاً
🔹 دليل الإثبات: إعلان معلَّق وآخر منتهٍ وثالث نشط + التأكد أن الشاشة تعرض النشط فقط
🔹 فحصك المباشر: فحص مباشر بإعلانات تجريبية بالحالات الثلاث
```

### 2.3 إعادة التحقق من الإعلان لحظة الضغط على "تعزيز"
```
🔹 النوع: كود
🔹 المدخلات: القرار من موجز مرحلة 11: إعادة جلب حالة الإعلان من قاعدة البيانات مباشرة قبل الانتقال لشاشة الدفع
🔹 داخل النطاق: استعلام خفيف (SELECT status, boost_expires_at WHERE id = ?) يتم عند الضغط على الزر، لا عند تحميل الشاشة
🔹 لماذا؟ تفادي حالة نادرة لكن واردة: إعلان يُعزَّز من جلسة أخرى بالتزامن أثناء تصفح هذه الشاشة
🔹 دليل الإثبات: محاكاة الحالة يدوياً — تعزيز إعلان مباشرة من قاعدة البيانات بينما المستخدم التجريبي في شاشة الاختيار، ثم الضغط على تعزيز → يجب ظهور رسالة "هذا الإعلان مُعزَّز بالفعل" لا الانتقال لشاشة دفع
```

### 2.4 عرض السعر النهائي قبل الانتقال
```
🔹 النوع: كود
🔹 داخل النطاق: حساب السعر (الإعلان × الباقة) وعرضه بوضوح في شاشة تأكيد قبل أي استدعاء API
🔹 فحصك المباشر: التأكد أن المستخدم يرى السعر النهائي بوضوح قبل الضغط على "أكمل الدفع"، لا بعده
```

## 🧩 القطعة 3 — Subscription Screen

### 3.1 جلب خطط الاشتراك وعرض الخطة الحالية
```
🔹 النوع: كود
🔹 المدخلات: 4 خطط من Seed Data الأصلي
🔹 داخل النطاق: جدول مقارنة واضح + تمييز بصري للخطة النشطة حالياً للمستخدم
🔹 خارج النطاق: لا زر "اشترك" على الخطة النشطة والسارية — "خطتك الحالية" نصياً فقط
🔹 دليل الإثبات: مستخدم تجريبي بخطة نشطة → التأكد أن زر الشراء مستبدَل بنص توضيحي
🔹 فحصك المباشر: تجربة بحسابين مختلفين — واحد بخطة واحد بدون خطة
```

### 3.2 تحذير عدم الاسترداد (قبل الانتقال لشاشة الدفع)
```
🔹 النوع: كود
🔹 المدخلات: القرار المُؤكَّد: لا تناسب زمني (No Proration)
🔹 داخل النطاق: حوار تأكيد يظهر عند اختيار خطة مختلفة عن الحالية، نصه الحرفي: "سيتم تطبيق الخطة الجديدة فوراً، بدون استرداد للمدة المتبقية من خطتك الحالية"
🔹 خارج النطاق: لا يظهر هذا الحوار للمستخدم بدون خطة حالية (لا شيء ليُستردَّ)
🔹 فحصك المباشر: تجربة الترقية بمستخدم لديه خطة نشطة → التأكد من ظهور الحوار قبل الانتقال لأي شاشة دفع
```

## 🧩 القطعة 4 — Payment WebView Screen

### 4.1 استدعاء create-payment (Stub مؤقت للسبرنت ده)
```
🔹 النوع: كود
🔹 المدخلات: العلم بأن create-payment الفعلية ستُبنى في السبرنت 6
🔹 داخل النطاق: Stub بسيط (دالة وهمية) يُرجِع رابط iframe تجريبي ثابت من Paymob Sandbox فقط بهدف اختبار سلوك الـ WebView — لا منطق حقيقي
🔹 لماذا Stub؟ لفصل اختبار سلوك WebView (مسؤولية هذا السبرنت) عن اختبار منطق الدفع الفعلي (مسؤولية السبرنت 6) بشكل نظيف
🔹 دليل الإثبات: تحميل iframe Paymob Sandbox فعلياً في الشاشة (الصفحة تظهر، لا شاشة بيضاء أو خطأ)
```

### 4.2 مراقبة توجيهات URL (Navigation Events)
```
🔹 النوع: كود
🔹 داخل النطاق: onNavigationRequest يراقب كل تغيير في URL، يكتشف صفحة النجاح/الفشل من Paymob عبر URL patterns المُحدَّدة في وثائق Paymob Sandbox
🔹 المُخرَج المطلوب: عند اكتشاف URL النجاح → عرض "جاري تأكيد الدفع..." (لا نجاح فوري) + بدء الاستماع لـ Supabase Realtime على جدول transactions
🔹 دليل الإثبات: تسجيل log يُثبت تلقّي حدث النجاح من Paymob Sandbox وعدم الانتقال لشاشة النجاح فوراً
🔹 فحصك المباشر: التأكد بنفسك أن التطبيق لا يعرض "تم الدفع" فور توجيه Paymob للصفحة الناجحة — يبقى في "جاري التأكيد..." حتى يصل تأكيد الـ Webhook (السبرنت 6)
```

### 4.3 مهلة زمنية + إغلاق آمن للـ WebView
```
🔹 النوع: كود
🔹 المدخلات: القرار من موجز مرحلة 11: مهلة 45 ثانية بعد توجيه النجاح
🔹 داخل النطاق: بعد 45 ثانية بدون تأكيد Webhook → رسالة "جاري المعالجة، ستصلك إشعار عند الاكتمال" + السماح للمستخدم بالخروج
🔹 خارج النطاق: ⚠️ لا رسالة "فشل" كاذبة عند انتهاء المهلة — المعاملة قد تكون ناجحة لكن الـ Webhook تأخّر
🔹 فحصك المباشر: محاكاة انتهاء المهلة (تعطيل Realtime مؤقتاً) → التأكد من ظهور رسالة "جاري المعالجة" لا رسالة فشل
```

### 4.4 إغلاق WebView في منتصف الدفع
```
🔹 النوع: كود
🔹 داخل النطاق: الضغط على رجوع أو إغلاق أثناء تحميل iframe → المعاملة تبقى pending نظيفة
🔹 دليل الإثبات: فحص جدول transactions بعد الإغلاق المتعمَّد → صفر تغيير في الحالة، المعاملة pending كما كانت
🔹 فحصك المباشر: فتح شاشة الدفع، الإغلاق فوراً قبل أي تفاعل، فحص قاعدة البيانات بنفسك
```

## ✅ معيار اكتمال السبرنت 5

عند اكتمال كل الصناديق، واجهات الدفع الثلاثة تعمل بشكل آمن ومتوقَّع، ومرجع HMAC جاهز للسبرنت القادم. التطبيق لا يُفعِّل أي شيء بعد — هذا متعمَّد تماماً.

الخطوة التالية هي السبرنت 6 (Edge Functions الدفع الفعلية: create-payment + payment-webhook + boost-ad) — وهو أخطر سبرنت مالياً في كل المشروع. قولي لما تخلص السبرنت 5 وتختبره.
