## 🧩 القطعة 1 — إدارة البلاغات

### 1.1 قائمة البلاغات الواردة
```
🔹 النوع: كود
🔹 داخل النطاق: جلب كل البلاغات مرتبة بالأحدث + فلترة بالحالة (جديد/قيد المعالجة/محلول)
🔹 بيانات كل بلاغ: اسم المُبلِّغ، الإعلان المُبلَّغ عنه، سبب البلاغ، التاريخ، الحالة
🔹 خارج النطاق: لا حذف للبلاغات — حل فقط
🔹 دليل الإثبات: 5 بلاغات تجريبية بحالات مختلفة → التأكد من ظهورها مرتبة صح
🔹 فحصك المباشر: الفلترة بـ "جديد" تُظهر البلاغات الجديدة فقط فعلاً
```

### 1.2 صفحة تفاصيل البلاغ + الإجراءات
```
🔹 النوع: كود
🔹 داخل النطاق: عرض تفاصيل الإعلان المُبلَّغ عنه + 3 إجراءات واضحة:
   - "تجاهل البلاغ" → حالة البلاغ: dismissed + Audit Log
   - "إخفاء الإعلان" → status الإعلان: hidden + Audit Log
   - "حظر المعلن" → الانتقال لصفحة إجراء الحظر (القطعة 2.3)
🔹 خارج النطاق: لا حذف نهائي للإعلان من لوحة الإدارة (Soft Delete فقط)
🔹 دليل الإثبات: تنفيذ "إخفاء إعلان" تجريبي → فتح التطبيق بنفس الحساب → الإعلان غير مرئي
🔹 فحصك المباشر: التأكد أن is_hidden = true في قاعدة البيانات + Audit Log مسجَّل
```

### 1.3 إحصائيات البلاغات في Dashboard
```
🔹 النوع: كود
🔹 داخل النطاق: إضافة رقم خامس للـ Dashboard من السبرنت 7: عدد البلاغات غير المحلولة
🔹 فحصك المباشر: مطابقة الرقم باستعلام SQL يدوي مباشرة
```

## 🧩 القطعة 2 — إدارة المستخدمين

### 2.1 صفحة بحث المستخدمين
```
🔹 النوع: كود
🔹 داخل النطاق: بحث برقم الهاتف أو الاسم + عرض: تاريخ التسجيل، trust_score، حالة التوثيق، عدد الإعلانات، عدد البلاغات الواردة ضده
🔹 خارج النطاق: لا تعديل على بيانات المستخدم من لوحة الإدارة (عرض فقط)
🔹 دليل الإثبات: بحث برقم هاتف حساب تجريبي → ظهور كل البيانات المذكورة أعلاه
```

### 2.2 User Activity Log — سجل نشاط المستخدم
```
🔹 النوع: كود
🔹 المدخلات: إضافة جدول user_activity_log جديد (غير موجود في الـ 34 جدول الأصلية)
🔹 هيكل الجدول:
   - user_id, action_type, metadata (JSONB), ip_address, created_at
   - action_type ENUM: login_success, login_failed, otp_requested,
     payment_attempted, payment_completed, ad_published, account_deletion_requested
🔹 داخل النطاق:
   - إنشاء الجدول + RLS (المستخدم لا يرى سجله، فريق الدعم فقط)
   - إضافة تسجيل في Edge Functions الموجودة:
     * request-otp → يسجّل otp_requested
     * create-payment → يسجّل payment_attempted
     * payment-webhook عند النجاح → يسجّل payment_completed
     * create-ad عند النجاح → يسجّل ad_published
🔹 خارج النطاق: ⚠️ لا تعديل على منطق أي Edge Function نفسه — إضافة سطر تسجيل فقط في نهاية كل دالة
🔹 دليل الإثبات: تنفيذ عملية دفع تجريبية كاملة → فحص user_activity_log يُظهر: otp_requested ← payment_attempted ← payment_completed بالترتيب
🔹 فحصك المباشر: قراءة الصفوف الثلاثة بالترتيب الزمني من لوحة Supabase مباشرة
```

### 2.3 تعليق حساب / حظر حساب
```
🔹 النوع: كود
🔹 داخل النطاق:
   - تعليق مؤقت: user_status = 'suspended' + تحديد مدة (24 ساعة / 7 أيام / 30 يوم)
   - حظر دائم: user_status = 'banned'
   - كلاهما: إبطال كل جلسات المستخدم الحالية فوراً + Audit Log
🔹 نقطة حرجة: إبطال الجلسات يتم عبر Supabase Auth Admin API (signOut للمستخدم المحدد) من جانب الخادم، لا انتظار انتهاء الجلسة طبيعياً
🔹 دليل الإثبات: تعليق حساب تجريبي → محاولة استخدام token موجود لذلك الحساب → رفض فوري
🔹 فحصك المباشر: تجربة الاستدعاء بـ token المُعلَّق عبر Postman → 401، لا 200
```

### 2.4 رفع التعليق / إلغاء الحظر
```
🔹 النوع: كود
🔹 داخل النطاق: إعادة user_status إلى active + Audit Log بمن رفع التعليق ولماذا (حقل نص اختياري)
🔹 فحصك المباشر: تسجيل دخول بالحساب بعد رفع التعليق → نجاح
```

## 🧩 القطعة 3 — إعدادات النظام

### 3.1 عرض وتعديل إعدادات النظام
```
🔹 النوع: كود
🔹 المدخلات: جدول الإعدادات الـ 14 من Seed Data الأصلي
🔹 داخل النطاق: صفحة تعرض كل الإعدادات في جدول قابل للتعديل المباشر
   - فئات: حدود النشر، أسعار الـ Boost، رسائل النظام، الميزات المُفعَّلة/المُعطَّلة
🔹 ⚠️ نقطة حرجة: التعديل يُسجَّل في Audit Log مع القيمة القديمة والجديدة معاً
🔹 دليل الإثبات: تعديل إعداد واحد → Audit Log يُظهر القيمة القبل والبعد بوضوح
🔹 فحصك المباشر: قراءة صف Audit Log مباشرة وتأكيد وجود الحقلين old_value وnew_value
```

### 3.2 Feature Flags (تفعيل/تعطيل ميزات بدون نشر كود)
```
🔹 النوع: كود
🔹 داخل النطاق: إضافة 3 Feature Flags أساسية كإعدادات في نفس الجدول:
   - enable_kyc_verification (true/false)
   - enable_boost_feature (true/false)
   - maintenance_mode (true/false) — يُظهر شاشة صيانة للمستخدمين
🔹 Flutter يقرأ هذه القيم عند فتح التطبيق ويتصرف وفقاً لها
🔹 دليل الإثبات: تفعيل maintenance_mode من لوحة الإدارة → التطبيق يعرض شاشة صيانة فعلاً
🔹 فحصك المباشر: تجربة التفعيل والتعطيل بنفسك على التطبيق
```
