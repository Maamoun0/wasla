## 🧩 القطعة 1 — تهيئة Firebase FCM في Flutter

### 1.1 الربط الفعلي بـ Firebase (الإعداد موجود في pubspec، غير مُفعَّل)
```
🔹 النوع: إعداد + كود
🔹 المدخلات: مشروع Firebase جديد أو موجود (مختلف عن Supabase)
🔹 داخل النطاق:
   - إضافة google-services.json لـ Android
   - إضافة GoogleService-Info.plist لـ iOS
   - تهيئة FirebaseMessaging في main.dart
🔹 خارج النطاق: ⚠️ كلا الملفين في .gitignore من اليوم الأول (تأكد قبل أي Commit)
🔹 دليل الإثبات: FirebaseMessaging.instance.getToken() يُرجِع token حقيقي (لا null)
🔹 فحصك المباشر: طباعة الـ token في console وتأكيد أنه سلسلة نصية طويلة غير فارغة
```

### 1.2 طلب إذن الإشعارات في السياق الصحيح
```
🔹 النوع: كود
🔹 المدخلات: قاعدة UX من مرحلة الثغرات — طلب الإذن في السياق لا عند فتح التطبيق
🔹 داخل النطاق: طلب الإذن عند:
   - أول مرة يحفظ المستخدم Watchlist (سياق منطقي: "سنخطرك عند ظهور إعلان مناسب")
   - لا عند Splash Screen أو Onboarding
🔹 دليل الإثبات: فتح التطبيق لأول مرة → لا طلب إذن. حفظ أول Watchlist → يظهر طلب الإذن
🔹 فحصك المباشر: تجربة التسلسل الكامل على iOS (الأكثر صرامة في الأذونات) وAndroid
```

### 1.3 حفظ Device Token في جدول device_tokens
```
🔹 النوع: كود
🔹 المدخلات: جدول device_tokens الجاهز من إضافات المرحلة 0
🔹 داخل النطاق:
   - حفظ Token عند أول تسجيل دخول ناجح
   - تحديثه إن تغيّر (FCM يغيّر الـ token أحياناً)
   - حذفه عند تسجيل الخروج (لا إشعارات لمستخدم خرج)
🔹 دليل الإثبات: تسجيل دخول تجريبي + فحص جدول device_tokens → صف جديد بالـ token والمنصة
🔹 فحصك المباشر: فحص الجدول من لوحة Supabase بعد الدخول مباشرة
```

## 🧩 القطعة 2 — Edge Function: `notify-watchlist-match`

### 2.1 الـ Trigger في قاعدة البيانات
```
🔹 النوع: كود
🔹 داخل النطاق: Database Trigger على جدول ads — عند إدراج إعلان جديد بحالة active يستدعي Edge Function notify-watchlist-match
🔹 خارج النطاق: لا استدعاء من Flutter أو من create-ad مباشرة — من قاعدة البيانات فقط
🔹 دليل الإثبات: تغيير حالة إعلان تجريبي من pending إلى active يدوياً → الـ Edge Function تُستدعى (يُتحقَّق من Supabase Function logs)
🔹 فحصك المباشر: قراءة Function logs في لوحة Supabase بعد التغيير اليدوي
```

### 2.2 منطق المطابقة (Matching)
```
🔹 النوع: كود
🔹 داخل النطاق: استعلام يجد كل Watchlist محفوظة تطابق الإعلان الجديد بثلاثة معايير:
   - نفس category_id
   - نفس governorate_id (أو المدينة إن حُدِّدت)
   - السعر ضمن نطاق user_min_price وuser_max_price (إن حُدِّدا)
🔹 لكل مطابقة: إرسال FCM لكل device_token المرتبط بذلك المستخدم
🔹 ⚠️ نقطة حرجة: مستخدم بجهازين يجب أن يتلقى الإشعار على الجهازين
🔹 دليل الإثبات: Watchlist تجريبية + إعلان يطابقها → إشعار يصل على الجهاز فعلاً
🔹 فحصك المباشر: رؤية الإشعار يصل على الجهاز الحقيقي بنفسك، لا الاعتماد على logs فقط
```

### 2.3 منع الإشعارات المتكررة
```
🔹 النوع: كود
🔹 داخل النطاق: تسجيل كل إشعار watchlist مُرسَل في جدول watchlist_notifications (user_id + ad_id + sent_at)، قبل الإرسال التحقق من عدم إرساله لنفس المستخدم عن نفس الإعلان مسبقاً
🔹 دليل الإثبات: تشغيل الـ Trigger مرتين على نفس الإعلان → الإشعار يصل مرة واحدة فقط
🔹 فحصك المباشر: عدّ الإشعارات الواصلة = 1 لا 2
```

## 🧩 القطعة 3 — Edge Function: `notify-ad-status`

### 3.1 الـ Trigger عند تغيير حالة الإعلان
```
🔹 النوع: كود
🔹 داخل النطاق: Database Trigger على جدول ads — عند تغيير status من pending إلى active أو rejected يستدعي Edge Function notify-ad-status
🔹 خارج النطاق: تغيير الحالة من Flutter (مثل تعليق إعلان من المعلن نفسه) لا يُرسِل إشعاراً
🔹 دليل الإثبات: قبول إعلان من لوحة الإدارة → إشعار "تم قبول إعلانك" يصل للمعلن
🔹 فحصك المباشر: رؤية الإشعار يصل على جهاز المعلن التجريبي بنفسك
```

### 3.2 نصوص الإشعارات بصوت العلامة
```
🔹 النوع: كود
🔹 داخل النطاق: نصوص محددة مسبقاً (لا يُولِّدها الذكاء الاصطناعي في runtime):
   - قبول: "✅ إعلانك '{{title}}' اتنشر وبقى مرئي للجميع!"
   - رفض: "❌ إعلانك '{{title}}' اترفض. السبب: {{reason}}"
🔹 خارج النطاق: لا Localization معقد الآن — عربية فقط
🔹 فحصك المباشر: التأكد أن {{title}} يظهر باسم الإعلان الفعلي، لا "undefined" أو فراغ
```

## 🧩 القطعة 4 — تفضيلات الإشعارات (في شاشة الإعدادات Flutter)

### 4.1 إعدادات تفضيلات الإشعارات
```
🔹 النوع: كود
🔹 المدخلات: الثغرة المُحدَّدة سابقاً — لا يوجد تحكم في أنواع الإشعارات
🔹 داخل النطاق: 3 تبديلات (Switches) في شاشة الإعدادات:
   - إشعارات Watchlist (افتراضي: مُفعَّل)
   - إشعارات حالة الإعلان (افتراضي: مُفعَّل)
   - إشعارات عروض خاصة (افتراضي: مُفعَّل) — للمستقبل
🔹 التخزين: عمود notification_preferences (JSONB) على جدول users
🔹 التطبيق: Edge Functions تتحقق من تفضيلات كل مستخدم قبل الإرسال
🔹 دليل الإثبات: تعطيل إشعارات Watchlist + نشر إعلان مطابق → لا إشعار يصل
🔹 فحصك المباشر: تجربة التعطيل بنفسك والتأكد من غياب الإشعار فعلاً
```

## 🧩 القطعة 5 — معالجة الإشعارات في الـ Foreground والـ Background

### 5.1 Foreground: إشعار داخلي عند فتح التطبيق
```
🔹 النوع: كود
🔹 داخل النطاق: عند وصول إشعار والتطبيق مفتوح:
   - iOS: FCM لا يعرض الإشعار تلقائياً في الـ Foreground → عرض Snackbar أو InApp notification
   - Android: FCM يعرضه تلقائياً لكن يمكن تخصيصه
🔹 دليل الإثبات: إرسال إشعار تجريبي والتطبيق مفتوح على iOS → Snackbar يظهر
```

### 5.2 Tap على الإشعار → Navigation صحيح
```
🔹 النوع: كود
🔹 داخل النطاق:
   - Tap على إشعار Watchlist → يفتح Ad Detail Screen للإعلان المحدَّد مباشرة
   - Tap على إشعار حالة إعلان → يفتح My Ads Screen
🔹 دليل الإثبات: tap فعلي على كل نوع إشعار على جهاز حقيقي
🔹 فحصك المباشر: تجربة الـ tap بنفسك والتأكد من الوصول للشاشة الصحيحة
```
