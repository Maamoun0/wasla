## 🧩 القطعة 1 — نموذج البيانات (DraftAd) — بناء بدون منطق بعد

### 1.1 بناء كلاس `DraftAd` (بيانات فقط، صفر منطق)
```
🔹 النوع: كود
🔹 المدخلات: المواصفة الكاملة من موجز "المهمة ب" (مرحلة 9) — كل الحقول المذكورة فيها بالضبط
🔹 داخل النطاق: ملف واحد يحتوي DraftAd + DraftImage (immutable، يُفضَّل freezed أو ما يعادله)
🔹 خارج النطاق: ⚠️ صفر دوال تعديل (setCategory، updateField...) في هذه الخطوة — بيانات فقط بدون أي منطق
🔹 المُخرَج المطلوب: كلاس يُبنى بنجاح (flutter pub get + بناء ناجح بدون أخطاء Type)
🔹 دليل الإثبات: محتوى الملف كاملاً + نتيجة flutter analyze على هذا الملف تحديداً
🔹 فحصك المباشر: قراءة الحقول بنفسك ومطابقتها واحداً واحداً مع القائمة في الموجز الأصلي (لا تثق أن الوكيل "غطى كل شيء")
🔹 عند الفشل: أي حقل ناقص يُعاد قبل الانتقال للقطعة 2 — بناء الـ Provider فوق نموذج بيانات ناقص يُكلِّف إعادة عمل لاحقاً
```

### 1.2 بناء Enums المساعدة (WizardStep وPriceType إن لم تكونا موجودتين)
```
🔹 النوع: كود
🔹 داخل النطاق: WizardStep (category, details, photos, location, preview) + PriceType إن لم يكن مُعرَّفاً مسبقاً في الكود الأصلي من المرحلة 8
🔹 خارج النطاق: تحقق أولاً هل PriceType مُعرَّف بالفعل في كود Flutter الموجود من قبل (Ad Detail Screen المكتملة) — إن وُجد، استخدمه بدل تكراره
🔹 فحصك المباشر: بحث نصي في المشروع عن "PriceType" قبل اعتماد الناتج، للتأكد من عدم وجود تكرار يُسبِّب تعارضاً لاحقاً
```

## 🧩 القطعة 2 — PostAdWizardProvider (المنطق، مقسَّم لخمس خطوات منفصلة)

### 2.1 هيكل الـ Provider الأساسي + reset()
```
🔹 النوع: كود
🔹 المدخلات: ناتج القطعة 1
🔹 داخل النطاق: StateNotifier فارغ يحمل DraftAd ابتدائي + دالة reset() فقط
🔹 خارج النطاق: ⚠️ صفر دوال تعديل أخرى بعد — هيكل + reset فقط
🔹 دليل الإثبات: محتوى الملف
🔹 فحصك المباشر: استدعاء reset() يدوياً في كود اختباري بسيط والتأكد أن الحالة تعود لقيمها الابتدائية تماماً
```

### 2.2 setCategory() — **أهم دالة في كل الـ Provider، مهمة منفصلة بمفردها**
```
🔹 النوع: كود
🔹 المدخلات: التحذير الصريح من موجز "المهمة ب": يجب مسح dynamicFieldValues بالكامل إذا تغيّر القسم
🔹 داخل النطاق: دالة setCategory(categoryId, subcategoryId) فقط
🔹 خارج النطاق: لا دوال أخرى في هذه الخطوة
🔹 المُخرَج المطلوب: منطق يقارن القيمة الجديدة بالقديمة، ويمسح dynamicFieldValues فقط عند الاختلاف الفعلي
🔹 دليل الإثبات: Unit Test واحد على الأقل مكتوب الآن (لا لاحقاً) يثبت السلوك: تعيين قسم، إضافة قيم حقول، تغيير القسم، التأكد أن الحقول فارغة
🔹 فحصك المباشر: قراءة الـ Unit Test بنفسك والتأكد أنه يختبر فعلاً الحالتين (نفس القسم لا يمسح / قسم مختلف يمسح)، لا اختباراً سطحياً يثبت حالة واحدة فقط
🔹 عند الفشل: هذه الدالة هي مصدر أكبر فجوة مذكورة في الموجز الأصلي — لا تُقبَل بدون الاختبار المذكور أعلاه يعمل فعلياً
```

### 2.3 دوال الحقول والصور
```
🔹 النوع: كود
🔹 داخل النطاق: updateField(fieldId, value)، addImage، removeImage، reorderImages، setCoverImage
🔹 خارج النطاق: لا منطق رفع فعلي للصور هنا (ده القطعة الخاصة بشاشة الصور في سبرنت قادم) — فقط إدارة الحالة المحلية للقائمة
🔹 دليل الإثبات: محتوى الملف + توضيح مختصر لمنطق reorderImages تحديداً (كيف يُحدَّد الغلاف بعد إعادة الترتيب)
🔹 فحصك المباشر: تتبّع منطق reorderImages يدوياً بمثال بسيط (3 صور، إعادة ترتيب، التأكد أن أول عنصر = الغلاف)
```

### 2.4 دوال الموقع والسعر
```
🔹 النوع: كود
🔹 داخل النطاق: setLocation(governorateId, cityId, districtId, lat, lng)، setPriceType()، setPrice()
🔹 خارج النطاق: لا منطق تحقق من حدود السعر هنا بعد (ده جزء من isStepValid في الخطوة التالية)
🔹 دليل الإثبات: محتوى الملف
```

### 2.5 goToStep() + isStepValid() — **منطق التحقق الكامل**
```
🔹 النوع: كود
🔹 المدخلات: حدود التحقق المُحدَّدة في الموجز الأصلي (عنوان 10-80، وصف 20-1000، إلخ) + موجز "المهمة هـ" لحدود السعر
🔹 داخل النطاق: goToStep(WizardStep) + isStepValid(WizardStep) تُغطي كل خطوة بمنطقها الخاص
🔹 المُخرَج المطلوب: دالة تحقق منفصلة منطقياً لكل خطوة (لا دالة واحدة ضخمة بشروط متشابكة يصعب تتبّعها)
🔹 دليل الإثبات: Unit Tests تغطي على الأقل: عنوان بـ9 أحرف يُرفَض، عنوان بـ81 حرفاً يُرفَض، حقل إلزامي فارغ يمنع التقدّم، سعر سالب يُرفَض
🔹 فحصك المباشر: قراءة كل اختبار من الاختبارات المذكورة، التأكد أنها فعلاً تستخدم القيم الحدّية (9 و81، لا 5 و100 مثلاً) — اختبار القيم الحدّية تحديداً هو ما يكشف أخطاء "أكبر من" مقابل "أكبر من أو يساوي"
```

## 🧩 القطعة 3 — Ad Form Screen

### 3.1 دالة جلب category_fields (طبقة بيانات، بدون واجهة بعد)
```
🔹 النوع: كود
🔹 المدخلات: بنية جدول category_fields من wasla-schema.sql الأصلي
🔹 داخل النطاق: دالة واحدة تجلب الحقول مرتبة بـ display_order، مع field_options المرتبطة
🔹 خارج النطاق: صفر واجهة Flutter في هذه الخطوة
🔹 دليل الإثبات: استدعاء فعلي للدالة بقسم تجريبي من بيانات Staging، والناتج الكامل كنص JSON
🔹 فحصك المباشر: مقارنة الناتج بما هو موجود فعلياً في جدول category_fields على Staging مباشرة من لوحة Supabase
```

### 3.2 مكوّن `DynamicFieldBuilder` (Widget معزول، قابل للاختبار بمفرده)
```
🔹 النوع: كود
🔹 المدخلات: أنواع الحقول الستة من الموجز الأصلي (text, number, select, multi_select, boolean, range)
🔹 داخل النطاق: Widget واحد يستقبل تعريف حقل ويُخرج العنصر المناسب فقط — لا شاشة كاملة بعد
🔹 خارج النطاق: لا ربط بـ Provider في هذه الخطوة — Widget مستقل قابل للاختبار بمعزل تام (Storybook-style)
🔹 المُخرَج المطلوب: ستة أنواع تعمل بصرياً، خصوصاً range (حقلان من/إلى مع تحقق من ≤)
🔹 دليل الإثبات: Widget Test واحد لكل نوع من الستة على الأقل
🔹 فحصك المباشر: تشغيل الـ Widget Tests بنفسك ورؤية الستة كلها خضراء
```

### 3.3 الشاشة الكاملة (Ad Form Screen) — الربط النهائي
```
🔹 النوع: كود
🔹 المدخلات: نواتج 2.x و3.1 و3.2 مجتمعة
🔹 داخل النطاق: الشاشة الكاملة — حقلا العنوان/الوصف الثابتان + قائمة DynamicFieldBuilder + ربط بـ PostAdWizardProvider + زر التالي مرتبط بـ isStepValid
🔹 خارج النطاق: عدم بناء شاشات الصور/الموقع/المعاينة الآن — فقط هذه الشاشة
🔹 المُخرَج المطلوب: شاشة تعمل من البداية للنهاية لهذه الخطوة تحديداً
🔹 دليل الإثبات: تسجيل فيديو قصير أو وصف خطوة بخطوة للتجربة اليدوية الفعلية على المحاكي
🔹 فحصك المباشر (تجربة يدوية فعلية، لا قراءة كود فقط):
   ☐ اختيار قسمين مختلفين يعطي حقولاً مختلفة فعلياً
   ☐ تجاوز 80 حرفاً في العنوان يمنع التقدّم برسالة عربية واضحة
   ☐ قسم بلا حقول ديناميكية يعرض الشاشة بشكل سليم (عنوان ووصف فقط)
   ☐ الرجوع لخطوة سابقة افتراضية ثم العودة يُبقي القيم كما كانت
```

```
🔹 فحصك المباشر: تجربة الإلغاء (البقاء) والتأكيد (الخروج الفعلي مع مسح reset()) كلاهما يدوياً
```

### 4.2 اختبار الانحدار الكامل للسبرنت
```
🔹 النوع: كود (تشغيل أوامر)

🔹 المُخرَج المطلوب: صفر تحذيرات جديدة، صفر اختبارات فاشلة، بما في ذلك اختبارات OTP من السبرنت السابق
🔹 دليل الإثبات: الناتج الكامل
🔹 فحصك المباشر: التأكد أن اختبارات السبرنت 0 لسه بتنجح (هذا فحص الانحدار الحقيقي — لا تتأكد فقط من اختبارات السبرنت 1 الجديدة)
```

## ✅ معيار اكتمال السبرنت 1
