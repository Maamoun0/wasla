# ⚙️ وصلة (Wasla) — دليل تنفيذ السبرنت 10
### التحضير النهائي للإطلاق — الانتقال من Staging إلى Production

> هذا السبرنت لا يحتوي كود ميزات جديدة. كل خطوة فيه تحضير أو تأكيد أو نقل. الهدف: بيئة Production جاهزة بالكامل ومُختبَرة قبل أن يراها أي مستخدم حقيقي.

## 🧩 القطعة 1 — مراجعة أمنية شاملة قبل الإطلاق

### 1.1 مراجعة كل الـ RLS Policies (إلزامي من خطة الأمن)
```
🔹 النوع: مراجعة يدوية
🔹 داخل النطاق: مراجعة كل Policy موجودة في Staging وتصنيفها:
   - صح ✅ أو تحتاج تعديل ⚠️ أو يجب حذفها ❌
🔹 الأولويات:
   - جدول transactions: لا يوجد أي Policy تسمح بكتابة من العميل مباشرة
   - جدول device_tokens: المستخدم يرى فقط tokens الخاصة به
   - جدول id-documents bucket: لا وصول عام نهائياً
   - جدول user_activity_log: المستخدم لا يرى سجله
🔹 دليل الإثبات: قائمة بكل Policy مراجَعة مع تصنيفها
🔹 فحصك المباشر: اختبار فعلي لأكثر 3 جداول حساسية (transactions، id-documents، otp_requests) بـ anon key → رفض في كل العمليات غير المصرَّح بها صراحة
```

### 1.2 مسح شامل للأسرار في الكود
```
🔹 النوع: فحص آلي
🔹 داخل النطاق: تشغيل gitleaks (المُعدّ في السبرنت 0) على كل تاريخ Git
   git log --all --full-history يتحقق أيضاً من الـ Commits القديمة
🔹 المُخرَج المطلوب: صفر نتائج لأي مفتاح أو سر
🔹 دليل الإثبات: ناتج أمر gitleaks كاملاً
🔹 فحصك المباشر: قراءة الناتج بنفسك، خصوصاً أي تحذير بمستوى HIGH
```

### 1.3 اختبار استعادة النسخة الاحتياطية (من خطة النشر)
```
🔹 النوع: اختبار يدوي
🔹 داخل النطاق: تنزيل آخر نسخة احتياطية من Supabase Staging + محاولة استعادتها على مشروع Supabase مؤقت منفصل
🔹 لماذا الآن؟ لأن نسخة احتياطية لم تُختبَر استعادتها لا قيمة مؤكَّدة لها
🔹 دليل الإثبات: مشروع الاستعادة المؤقت يحتوي كل الجداول والبيانات بشكل صحيح
🔹 فحصك المباشر: SELECT COUNT(*) على 5 جداول رئيسية في المشروع المُستعاد ومقارنتها بـ Staging
🔹 بعد الانتهاء: حذف المشروع المؤقت فوراً
```

## 🧩 القطعة 3 — الانتقال إلى Production

### 3.1 تشغيل كل ملفات SQL على Production
```
🔹 النوع: تنفيذ مُتحكَّم فيه (لا وكيل — أنت شخصياً)
🔹 الترتيب الإلزامي:
   1. wasla-schema.sql الأصلي (34 جدول)
   2. wasla-phase0-schema-additions.sql (إضافات المرحلة 0)
   3. Seed Data (محافظات، أقسام، خطط الاشتراك)
   4. Cron Jobs (من السبرنت قبل 7)
   5. RLS Policies (نفس ما على Staging بعد مراجعة 1.1)
🔹 ⚠️ لا تُشغِّل أي بيانات اختبار أو تجريبية على Production
🔹 دليل الإثبات: SELECT COUNT(*) على الجداول الأساسية يُظهر الـ Seed Data فقط وصفر بيانات تجريبية
🔹 فحصك المباشر: مقارنة عدد الجداول على Production بـ Staging (يجب أن يكونا متساويَين)
```

### 3.2 نشر Edge Functions على Production
```
🔹 النوع: تنفيذ مُتحكَّم فيه
🔹 المدخلات: CI/CD من خطة النشر — موافقة يدوية إلزامية قبل النشر على Production
🔹 قائمة Edge Functions للنشر بالترتيب:
   - request-otp
   - ai-content-review
   - create-ad
   - submit-kyc-request
   - create-payment
   - payment-webhook
   - boost-ad
   - notify-watchlist-match
   - notify-ad-status
🔹 لكل دالة: التأكد أن Secrets الخاصة بـ Production (مفاتيح Live لا Sandbox) محفوظة في Supabase Production Secrets
🔹 دليل الإثبات: كل دالة تُختبَر بـ ping بسيط بعد النشر (لا بيانات حقيقية) وتُرجِع استجابة لا خطأ 500
🔹 فحصك المباشر: فحص لوحة Supabase → Edge Functions → كل دالة بحالة "Active"
```

### 3.3 تحديث ملف .env في Flutter للـ Production
```
🔹 النوع: كود
🔹 داخل النطاق: استبدال SUPABASE_URL وSUPABASE_ANON_KEY بقيم Production
🔹 ⚠️ هذا التغيير يُعمَل في فرع منفصل feature/production-config، يُدمَج في main فقط
   لا يُدمَج في develop أبداً
🔹 فحصك المباشر: بناء نسخة Release والتأكد أنها تتصل بـ Production لا Staging
   (يُتحقَّق بإنشاء مستخدم تجريبي ورؤيته في لوحة Supabase Production)
```

## 🧩 القطعة 4 — إعداد المراقبة على Production

### 4.1 Sentry على Production
```
🔹 النوع: كود
🔹 داخل النطاق: DSN خاص بـ Production (مختلف عن Staging) في ملف Flutter
🔹 اختبار إلزامي: استدعاء Sentry.captureException() يدوياً مرة واحدة
   → التأكد أن الخطأ يظهر فعلاً في لوحة Sentry قبل الإطلاق
🔹 فحصك المباشر: رؤية الخطأ التجريبي في لوحة Sentry بنفسك — لا تثق أنه "سيعمل"
```

### 4.2 PostHog على Production
```
🔹 النوع: كود
🔹 داخل النطاق: تسجيل الأحداث الأربعة المُحدَّدة في خطة النشر:
   - user_registered
   - ad_published
   - first_boost_purchased
   - subscription_started
🔹 اختبار إلزامي: تشغيل حدث user_registered تجريبي → يظهر في لوحة PostHog
🔹 فحصك المباشر: رؤية الحدث في PostHog بنفسك خلال دقيقة من التشغيل
```

### 4.3 تنبيه Sentry عند فشل payment-webhook
```
🔹 النوع: إعداد في Sentry
🔹 داخل النطاق: Alert Rule في Sentry: أي خطأ في payment-webhook → إشعار فوري على إيميلك
🔹 لماذا هذه الدالة تحديداً؟ لأن فشلها يعني معاملة مالية لم تُكتمَل بدون علمك
🔹 فحصك المباشر: إرسال خطأ تجريبي من payment-webhook → وصول إيميل التنبيه فعلاً
```
