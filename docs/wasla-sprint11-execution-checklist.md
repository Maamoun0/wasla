## 🧩 القطعة 1 — اختبار الرحلات الحرجة الأربع على Production

### 1.1 رحلة 1: التسجيل وOTP المحمي — على Production
```
🔹 النوع: اختبار يدوي
🔹 الجهاز: Android حقيقي + iOS حقيقي (كلاهما إلزامي)
🔹 الخطوات:
   ☐ طلب OTP لرقم جديد → يصل فعلاً (SMS حقيقي، لا Sandbox)
   ☐ طلب OTP 4 مرات متتالية → الرابع يُرفَض برسالة عربية واضحة
   ☐ إدخال كود خاطئ 5 مرات → الكود يُبطَل
   ☐ Checkbox الموافقة على الشروط إلزامي فعلاً
   ☐ الموافقة تُسجَّل في legal_acceptances على Production (فحص مباشر)
🔹 فحصك المباشر على كلا الجهازين — لا محاكي هنا
```

### 1.2 رحلة 2: نشر إعلان كامل — على Production
```
🔹 النوع: اختبار يدوي
🔹 الخطوات:
   ☐ اختيار قسم → حقول ديناميكية من Production (لا Staging)
   ☐ رفع 8 صور → Image Transformation يعمل (فحص Network requests)
   ☐ تحديد موقع بمنطقة من القاهرة → قائمة الأحياء تظهر
   ☐ معاينة مطابقة بصرياً لـ Ad Detail
   ☐ نشر → ai_risk_level محسوبة (layer_used مسجَّل في قاعدة البيانات)
   ☐ قطع الاتصال وسط الإرسال → لا صف يتيم في Production
   ☐ إعادة المحاولة → نجاح بدون تكرار
🔹 فحصك المباشر: فحص قاعدة بيانات Production مباشرة بعد كل نشر تجريبي
```

### 1.3 رحلة 3: التحقق من الهوية — على Production
```
🔹 النوع: اختبار يدوي
🔹 الخطوات:
   ☐ تصوير بطاقة هوية تجريبية (يمكن استخدام بطاقة شخصية لاختبار تجريبي فقط)
   ☐ رقم قومي بصيغة خاطئة → رفض محلي فوري بدون شبكة
   ☐ إرسال طلب → الصور في bucket id-documents لا يُفتَح برابط مباشر
   ☐ محاولة إرسال طلب ثانٍ → مرفوض
   ☐ قبول الطلب من لوحة الإدارة → badge يظهر في التطبيق فوراً
🔹 فحصك المباشر: محاولة فتح رابط وثيقة مباشرة في Production → 403
```

### 1.4 رحلة 4: الدفع — على Production بمفاتيح Live
```
🔹 النوع: اختبار يدوي بمبلغ حقيقي (أقل باقة Boost)
🔹 ⚠️ هذا الاختبار يستخدم بطاقة بنكية حقيقية — اختبر بأقل مبلغ ممكن
🔹 الخطوات:
   ☐ Boost إعلان → iframe Paymob Live يظهر
   ☐ إكمال الدفع فعلاً → is_boosted = true في Production
   ☐ user_activity_log يُظهر payment_completed
   ☐ Sentry لا يُسجِّل أي خطأ أثناء العملية
🔹 فحصك المباشر: رؤية is_boosted = true + boost_expires_at بتاريخ منطقي في Production
🔹 بعد الاختبار: إلغاء الـ Boost يدوياً من لوحة Paymob إن أمكن، أو اعتباره تكلفة اختبار
```

## 🧩 القطعة 2 — اختبار حالات الشبكة الضعيفة

### 2.1 Network Throttling على الرحلات الحرجة
```
🔹 النوع: اختبار يدوي
🔹 الأداة: تفعيل Network Throttling من أدوات المطوّر (Android Developer Options → Network throttling)
🔹 الإعداد: "Regular 3G" أو ما يعادله — شائع في المناطق الريفية المصرية
🔹 الخطوات:
   ☐ تحميل Home Screen على شبكة بطيئة → يظهر Loading indicator واضح لا شاشة بيضاء
   ☐ رفع صور على شبكة بطيئة → مؤشر تقدم يعمل لكل صورة
   ☐ نشر إعلان على شبكة بطيئة → لا timeout مبكر يُفشل العملية قبل اكتمالها
   ☐ فتح Payment WebView على شبكة بطيئة → صفحة Paymob تُحمَّل (قد تستغرق أكثر)
🔹 فحصك المباشر: كل الخطوات بنفسك على جهاز Android حقيقي
```

### 2.2 انقطاع كامل للإنترنت (Offline)
```
🔹 النوع: اختبار يدوي
🔹 الخطوات:
   ☐ تصفح الإعلانات بدون إنترنت → رسالة واضحة "لا يوجد اتصال"، لا crash
   ☐ محاولة نشر إعلان بدون إنترنت → رسالة واضحة بصوت العلامة
   ☐ استعادة الاتصال → التطبيق يعمل بشكل طبيعي بدون إعادة تشغيل
🔹 فحصك المباشر: لا شاشة بيضاء ولا crash في أي من هذه الحالات
```

## 🧩 القطعة 3 — اختبار التحمّل (Load Testing)

### 3.1 إعداد k6
```
🔹 النوع: كود (سكريبت k6)
🔹 المدخلات: k6 مثبَّت محلياً (brew install k6 أو npm install -g k6)
🔹 داخل النطاق: سكريبت بسيط يختبر نقطتَي الضغط الأكثر أهمية فقط
```

```javascript
// wasla-load-test.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },   // رفع تدريجي لـ 50 مستخدم
    { duration: '5m', target: 50 },   // ثبات عند 50 مستخدم
    { duration: '2m', target: 100 },  // رفع لـ 100 مستخدم
    { duration: '5m', target: 100 },  // ثبات عند 100 مستخدم
    { duration: '2m', target: 0 },    // هبوط تدريجي
  ],
  thresholds: {
    http_req_duration: ['p(95)<2000'], // 95% من الطلبات أسرع من 2 ثانية
    http_req_failed: ['rate<0.01'],    // أقل من 1% فشل
  },
};

const BASE_URL = 'YOUR_SUPABASE_STAGING_URL'; // Staging فقط، لا Production

export default function () {
  // نقطة 1: البحث والتصفح (الأكثر تكراراً)
  const searchRes = http.get(
    `${BASE_URL}/rest/v1/ads?status=eq.active&limit=20`,
    { headers: { 'apikey': 'YOUR_ANON_KEY' } }
  );
  check(searchRes, { 'search status 200': (r) => r.status === 200 });
  sleep(1);

  // نقطة 2: تفاصيل إعلان واحد
  const detailRes = http.get(
    `${BASE_URL}/rest/v1/ads?id=eq.TEST_AD_ID&limit=1`,
    { headers: { 'apikey': 'YOUR_ANON_KEY' } }
  );
  check(detailRes, { 'detail status 200': (r) => r.status === 200 });
  sleep(1);
}
```

```
🔹 ⚠️ يُشغَّل على Staging فقط — لا Production أبداً
🔹 دليل الإثبات: ملف نتائج k6 الكامل (k6 run wasla-load-test.js --out json=results.json)
🔹 فحصك المباشر: p(95) < 2000ms في النتائج = مقبول. أي تجاوز يعني تحسين Index مطلوب
```

### 3.2 تحليل النتائج واتخاذ إجراء
```
🔹 إذا p(95) > 2000ms على استعلام البحث:
   → EXPLAIN ANALYZE على الاستعلام في Supabase مباشرة
   → إضافة Index ناقص (إن وُجد) وإعادة الاختبار

🔹 إذا error rate > 1%:
   → فحص Supabase Dashboard → Database → Connections
   → رفع Connection Pool إن كان هناك اختناق
```
