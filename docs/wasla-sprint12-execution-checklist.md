## 🧩 القطعة 1 — بناء نسخ الإنتاج

### 1.1 بناء نسخة Android (APK/AAB موقَّعة)
```
🔹 النوع: تنفيذ يدوي (أنت شخصياً)
🔹 الأوامر:
   flutter build appbundle --release --obfuscate --split-debug-info=./debug-info
🔹 ⚠️ --obfuscate إلزامي (من خطة الأمن) لتشويه الكود في نسخة الإنتاج
🔹 فحصك المباشر:
   ☐ حجم الـ AAB معقول (عادة 30-80MB)
   ☐ تثبيت الـ APK Release على جهاز Android حقيقي والتأكد أنه يتصل بـ Production
```

### 1.2 بناء نسخة iOS (IPA موقَّعة)
```
🔹 النوع: تنفيذ يدوي على Mac
🔹 الأوامر:
   flutter build ios --release --obfuscate --split-debug-info=./debug-info
🔹 المتطلبات: Apple Developer Account + Provisioning Profile للإنتاج
🔹 فحصك المباشر:
   ☐ Xcode Archive يكتمل بدون أخطاء signing
   ☐ النسخة تعمل على iPhone حقيقي قبل الرفع
```

## 🧩 القطعة 2 — الرفع لـ Google Play Console

### 2.1 رفع AAB وإعداد الإصدار
```
🔹 النوع: يدوي في Google Play Console
🔹 الخطوات:
   ☐ رفع AAB على مسار "Internal Testing" أولاً (لا Production مباشرة)
   ☐ إضافة 5-10 مستخدمين داخليين كـ Internal Testers
   ☐ انتظار مراجعة Google (عادة ساعات لـ Internal Testing)
   ☐ اختبار من قِبَل المستخدمين الداخليين على أجهزتهم الحقيقية
   ☐ بعد 24-48 ساعة بدون مشاكل → ترقية لـ "Production"
```

### 2.2 إعداد صفحة التطبيق
```
🔹 الخطوات:
   ☐ وصف التطبيق بالعربية (500 حرف مختصر + 4000 حرف تفصيلي)
   ☐ أيقونة + Feature Graphic + لقطات الشاشة (من السبرنت 10)
   ☐ Data Safety Form مكتملة ومطابقة للواقع
   ☐ تصنيف المحتوى: "للجميع"
   ☐ رابط سياسة الخصوصية (من السبرنت 10)
```

### 2.3 الإطلاق التدريجي (Staged Rollout)
```
🔹 القرار المقترَح: لا إطلاق 100% فوراً
   → 10% من المستخدمين أول 48 ساعة
   → مراقبة Crash Rate + تقييمات
   → 50% بعد 48 ساعة إذا كل شيء هادئ
   → 100% بعد 5 أيام
🔹 شرط التوقف الفوري: Crash Rate > 1% → إيقاف الرولاوت فوراً
```

## 🧩 القطعة 3 — الرفع لـ App Store Connect

### 3.1 رفع عبر TestFlight أولاً
```
🔹 النوع: يدوي في Xcode + App Store Connect
🔹 الخطوات:
   ☐ رفع IPA عبر Xcode Organizer → App Store Connect
   ☐ إضافة مستخدمين داخليين على TestFlight
   ☐ اختبار 48 ساعة على TestFlight
   ☐ بعد نجاح TestFlight → إرسال للمراجعة الرسمية من Apple
```

### 3.2 تحضير نموذج مراجعة Apple
```
🔹 ⚠️ Apple أكثر صرامة من Google — هذه الأسئلة ستُسأل:
   - "ماذا يفعل التطبيق؟" → وصف واضح لمنصة الإعلانات المبوّبة
   - "لماذا تجمع الموقع؟" → لإظهار الإعلانات القريبة من المستخدم
   - "لماذا تجمع صور الهوية؟" → للتحقق من هوية المعلنين لحماية المستخدمين
   - "أين مسار حذف الحساب؟" → الإعدادات → حذف الحساب (يجب توثيق المسار خطوة بخطوة)
🔹 فحصك المباشر: اتباع كل مسار مذكور أعلاه بنفسك على iOS قبل إرسال النموذج
```

### 3.3 الاستعداد لمراجعة Apple (5-7 أيام عادةً)
```
🔹 أكثر أسباب الرفض شيوعاً لتطبيقات مشابهة:
   - مسار حذف الحساب غير واضح (مُعالَج في السبرنت 9)
   - رابط سياسة الخصوصية لا يعمل (تحقق مرة أخرى قبل الإرسال)
   - وصف التطبيق لا يطابق الوظائف الفعلية
🔹 إذا جاء رفض: اقرأ سبب الرفض بدقة → حدِّد فقط المشكلة المذكورة → أرسِل مجدداً
```

## 🧩 القطعة 4 — مراقبة الأسبوع الأول (أهم أسبوع في تاريخ المنصة)

### 4.1 جدول المراقبة اليومية
```
🔹 كل يوم في الأسبوع الأول، افتح هذه اللوحات بالترتيب:

الصباح (10 دقائق):
  ☐ Sentry → Crash Rate اليوم مقارنة بالأمس
  ☐ PostHog → Events: كم مستخدم سجّل؟ كم نشر إعلاناً؟
  ☐ Supabase → Database → Connections (لا اختناق)
  ☐ Supabase → Edge Functions → أي دالة فيها أخطاء متكررة؟

المساء (5 دقائق):
  ☐ Google Play Console → تقييمات جديدة؟ أي شكوى متكررة؟
  ☐ App Store Connect → نفس الشيء
```

### 4.2 معايير التدخل الفوري
```
🔹 توقف الإطلاق فوراً إذا:
   - Crash Rate > 1% في أي ساعة
   - payment-webhook يُسجِّل أخطاء متكررة
   - أي تقرير من مستخدم عن دفع بدون تفعيل

🔹 تدخل خلال ساعتين إذا:
   - OTP لا يصل لعدد كبير من المستخدمين
   - صور الإعلانات لا تُحمَّل على شبكات بعينها

🔹 عالِج في نهاية اليوم:
   - أي شكوى UX في التقييمات
   - أي خطأ Medium في Sentry
```

### 4.3 قناة تواصل مع المستخدمين الأوائل
```
🔹 أنشئ قبل الإطلاق:
   - رقم واتساب للدعم (مذكور في التطبيق)
   - بريد إلكتروني للدعم (support@wasla.app أو ما يعادله)
   - رد آلي واضح: "سيتم الرد خلال 24 ساعة"
🔹 الأسبوع الأول: راجع كل رسالة دعم بنفسك — هي مصدر ذهبي لفهم المشاكل الحقيقية قبل أي Analytics
```
