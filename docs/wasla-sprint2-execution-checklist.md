## 🧩 القطعة 1 — بيانات الأحياء (تسبق كل شيء، لأن Location Price Screen تعتمد عليها)

### 1.1 تجميع قائمة أحياء القاهرة الكبرى والإسكندرية
```
🔹 النوع: بحث
🔹 المدخلات: لا شيء — بحث من الصفر
🔹 داخل النطاق: قائمة بأسماء الأحياء الرسمية (القاهرة، الجيزة، القليوبية كجزء من "القاهرة الكبرى"، والإسكندرية)، كل حي مرتبط بالمدينة الصحيحة من جدول cities الموجود فعلاً
🔹 خارج النطاق: لا تعديل SQL في هذه الخطوة، تجميع بيانات فقط
🔹 المُخرَج المطلوب: ملف نصي/JSON بقائمة الأحياء، كل عنصر يحمل اسم الحي واسم المدينة المرتبط بها بالضبط كما هو مكتوب في جدول cities
🔹 دليل الإثبات: القائمة كاملة كنص، لا ملخص أو عدد فقط
🔹 فحصك المباشر: مراجعة عشوائية لـ5-6 أحياء معروفة لك شخصياً (مثل حي معروف في منطقتك) للتأكد من دقة التصنيف تحت المدينة الصحيحة
🔹 عند الفشل: أي حي مرتبط بمدينة خاطئة يُصحَّح قبل إدراج أي بيانات في قاعدة البيانات
```

### 1.2 إدراج البيانات في جدول districts على Staging
```
🔹 النوع: كود
🔹 المدخلات: القائمة المُعتمَدة من 1.1
🔹 داخل النطاق: سكريبت SQL إدراج (INSERT) فقط لجدول districts، تشغيله على wasla-staging حصراً
🔹 خارج النطاق: ⚠️ صفر تشغيل على wasla-production
🔹 دليل الإثبات: نص استعلام SELECT COUNT(*) FROM districts GROUP BY city_id بعد الإدراج
🔹 فحصك المباشر: فتح الجدول من لوحة Supabase والتأكد بصرياً من وجود البيانات مرتبطة بالمدن الصحيحة
```

## 🧩 القطعة 2 — Add Photos Screen (الأكثر تعقيداً تقنياً في السبرنت)

### 2.1 اختيار الصور + الضغط المحلي (بدون رفع بعد)
```
🔹 النوع: كود
🔹 المدخلات: حد 8 صور، هدف ضغط <500KB، أبعاد أقصى 1600px، جودة ~80% (من موجز "المهمة د")
🔹 داخل النطاق: منطق اختيار صور (image_picker) + ضغط (flutter_image_compress) محلياً فقط
🔹 خارج النطاق: ⚠️ صفر منطق رفع لـ Supabase Storage في هذه الخطوة
🔹 المُخرَج المطلوب: قائمة ملفات محلية مضغوطة، مع منع اختيار صورة تاسعة
🔹 دليل الإثبات: حجم فعلي لـ3 صور تجريبية قبل وبعد الضغط (بالكيلوبايت)
🔹 فحصك المباشر: التأكد بنفسك أن الحجم بعد الضغط فعلاً أقل من 500KB لكل صورة من الثلاث
```

### 2.2 دالة رفع صورة واحدة (معزولة، قابلة لإعادة الاستخدام)
```
🔹 النوع: كود
🔹 المدخلات: مسار temp_draft_id المُولَّد محلياً عند بدء الـ Wizard (من DraftAd)
🔹 داخل النطاق: دالة واحدة: رفع ملف واحد لمسار {user_id}/{temp_draft_id}/{index}.jpg، مع callback لتقدّم الرفع
🔹 خارج النطاق: لا تنسيق رفع متعدد الصور في هذه الخطوة — دالة لصورة واحدة فقط
🔹 دليل الإثبات: رفع تجريبي فعلي لصورة واحدة على Staging + الرابط الناتج
🔹 فحصك المباشر: فتح الرابط من لوحة Supabase Storage والتأكد أن الصورة موجودة فعلياً في المسار الصحيح
```

### 2.3 تنسيق الرفع المتوازي + إعادة المحاولة لكل صورة
```
🔹 النوع: كود
🔹 المدخلات: ناتج 2.2
🔹 داخل النطاق: رفع كل الصور المختارة بالتوازي (لا بالتتابع)، مؤشر تقدّم مستقل لكل صورة، زر إعادة محاولة يخص الصورة الفاشلة فقط
🔹 المُخرَج المطلوب: فشل صورة واحدة من 8 لا يوقف رفع الباقي
🔹 دليل الإثبات: تجربة فعلية — قطع الاتصال يدوياً أثناء رفع صورة واحدة من 3، ومراقبة الناتج
🔹 فحصك المباشر: رؤية الصورتين الأخريين تكتملان بنجاح بينما تظهر الثالثة بحالة "فشل" وزر إعادة محاولة مستقل
🔹 عند الفشل: إن أوقف فشل صورة واحدة كل العملية، هذا خطأ جوهري في التصميم يُصحَّح قبل أي خطوة تالية
```

### 2.4 إعادة الترتيب + الغلاف التلقائي + الحذف الفعلي
```
🔹 النوع: كود
🔹 داخل النطاق: ReorderableListView مربوط بـ reorderImages من Provider (السبرنت 1) + حذف صورة يحذفها فعلياً من Storage إن كانت مرفوعة
🔹 خارج النطاق: لا تعديل على منطق reorderImages نفسه في Provider — استخدامه كما هو من السبرنت السابق
🔹 دليل الإثبات: تجربة فعلية — إعادة ترتيب 3 صور، ثم حذف واحدة مرفوعة فعلياً
🔹 فحصك المباشر: فتح لوحة Supabase Storage بعد الحذف والتأكد أن الملف اختفى فعلياً، لا أنه فقط اختفى من الواجهة
```

### 2.5 الشاشة الكاملة + التحقق اليدوي الشامل
```
🔹 النوع: كود
🔹 المدخلات: نواتج 2.1 إلى 2.4 مجتمعة
🔹 المُخرَج المطلوب: شاشة Add Photos كاملة تعمل من البداية للنهاية
🔹 دليل الإثبات: وصف تجربة يدوية كاملة خطوة بخطوة
🔹 فحصك المباشر:
   ☐ اختيار صورة تاسعة يُمنَع برسالة واضحة
   ☐ لا يمكن التقدّم بدون صورة واحدة على الأقل
   ☐ أول صورة في الترتيب تظهر كغلاف بصرياً في الواجهة
```

## 🧩 القطعة 3 — Location Price Screen

### 3.1 القوائم المتسلسلة (محافظة → مدينة → منطقة)
```
🔹 النوع: كود
🔹 المدخلات: جدول districts المُعَدّ في القطعة 1
🔹 داخل النطاق: ثلاث قوائم منسدلة متتالية، كل واحدة تُفعَّل بعد اختيار التي قبلها
🔹 المُخرَج المطلوب: ⚠️ قائمة المنطقة تختفي بالكامل (لا تظهر فاضية) لأي مدينة خارج القاهرة الكبرى/الإسكندرية
🔹 دليل الإثبات: تجربة فعلية لمدينتين — واحدة من القاهرة الكبرى (تظهر فيها قائمة المنطقة)، وواحدة من محافظة أخرى (تختفي القائمة)
🔹 فحصك المباشر: رؤية الاختفاء الكامل بعينك، لا مجرد قائمة فارغة تبدو كخطأ بصري
```

### 3.2 خيار تحديد الموقع على الخريطة (اختياري)
```
🔹 النوع: كود
🔹 داخل النطاق: زر اختياري يفتح google_maps_flutter لتحديد lat/lng دقيقين
🔹 خارج النطاق: ⚠️ يجب ألا يكون إلزامياً للتقدّم في أي حالة
🔹 فحصك المباشر: التأكد أن إغلاق الخريطة بدون تحديد موقع لا يمنع المتابعة
```

### 3.3 نوع وقيمة السعر
```
🔹 النوع: كود
🔹 المدخلات: حدود السعر المُتفَق عليها (أكبر من صفر، أقل من 100,000,000 جنيه)
🔹 داخل النطاق: أربعة خيارات لنوع السعر، حقل السعر يظهر فقط لخيارين منهم، فاصل آلاف تلقائي
🔹 دليل الإثبات: Unit Test يثبت رفض سعر سالب وسعر صفر وسعر يتجاوز الحد الأعلى
🔹 فحصك المباشر: قراءة الاختبار بنفسك، التأكد أنه يغطي الحدود الثلاثة المذكورة تحديداً
```

### 3.4 الشاشة الكاملة + التحقق اليدوي
```
🔹 النوع: كود
🔹 فحصك المباشر:
   ☐ تغيير المحافظة يصفّر اختيار المدينة والمنطقة تلقائياً
   ☐ حقل السعر يظهر/يختفي فوراً عند تبديل نوع السعر
```

## 🧩 القطعة 4 — Ad Preview Screen

### 4.1 دالة `DraftAd.toPreviewAdModel()`
```
🔹 النوع: كود
🔹 المدخلات: شكل البيانات المتوقَّع من Ad Detail Screen المكتملة فعلياً (مرحلة 8)
🔹 داخل النطاق: دالة تحويل واحدة فقط، لا تعديل على Ad Detail Screen نفسها
🔹 خارج النطاق: ⚠️ ممنوع تعديل أي ملف من Ad Detail Screen الأصلية في هذه الخطوة
🔹 دليل الإثبات: ناتج التحويل لمسودة تجريبية كاملة، كنص JSON
🔹 فحصك المباشر: مطابقة الحقول يدوياً مع ما تتوقعه Ad Detail Screen فعلياً
```

### 4.2 الشاشة الكاملة بإعادة استخدام مكوّنات Ad Detail Screen
```
🔹 النوع: كود
🔹 المدخلات: ناتج 4.1
🔹 داخل النطاق: استخدام نفس الـ Widgets الفعلية من Ad Detail Screen، مع أزرار "تعديل" بجانب كل قسم تستدعي goToStep()
🔹 المُخرَج المطلوب: تطابق بصري كامل مع شاشة التفاصيل الحقيقية
🔹 دليل الإثبات: وصف مقارنة بصرية جنباً إلى جنب (أو لقطتا شاشة إن أمكن إرسالهما)
🔹 فحصك المباشر: مقارنتك الشخصية بعينك — هل تبدو الشاشتان متطابقتين فعلاً، لا "شبه متطابقتين"؟
🔹 عند الفشل: أي اختلاف بصري يعني عدم إعادة استخدام فعلية للمكوّنات — يُصحَّح بإعادة استخدام الـ Widget الأصلي حرفياً لا بناء نسخة مشابهة
```

### 4.3 معالجة الحقول غير المتاحة بعد + اختبار يدوي للضغط على "تعديل"
```
🔹 النوع: كود
🔹 داخل النطاق: عناصر نائبة واضحة (مثل "سيظهر بعد النشر") للحقول غير المتاحة في مرحلة المعاينة
🔹 فحصك المباشر: الضغط على "تعديل" بجانب الصور يفتح Add Photos Screen فعلياً مع البيانات الموجودة سليمة، لا فارغة
```

## ✅ معيار اكتمال السبرنت 2

عند اكتمال كل الصناديق، رحلة "نشر إعلان" تعمل فعلياً من اختيار القسم وحتى شاشة المعاينة الكاملة — كل شيء جاهز ما عدا الإرسال الفعلي لقاعدة البيانات. الخطوة التالية هي السبرنت 3 (الإرسال الفعلي عبر `create-ad` + فحص الذكاء الاصطناعي + شاشة النجاح) — وهي **أهم سبرنت في كل المشروع**، لأنها اللحظة التي يصبح فيها أول إعلان حقيقي منشوراً فعلياً على المنصة. سأقدّم نفس مستوى التقسيم الذرّي له عند وصولك لتلك النقطة.
