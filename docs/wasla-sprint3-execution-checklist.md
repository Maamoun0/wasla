## 🧩 القطعة 1 — Edge Function: `ai-content-review`

### 1.1 بناء الدالة الأساسية (استدعاء Claude API)
```
🔹 النوع: كود
🔹 المدخلات: القرار 0.1 — تمرير نص الإعلان + السعر + القسم لـ Claude API، طلب رد JSON مُهيكَل (مستوى خطورة + سبب + توصية)
🔹 داخل النطاق: Edge Function واحدة تستقبل (title, description, price, category) وتُرجِع (ai_risk_level, ai_review_notes)
🔹 خارج النطاق: ⚠️ صفر ربط بـ create-ad في هذه الخطوة — دالة مستقلة تُختبَر بمفردها أولاً
🔹 المُخرَج المطلوب: استدعاء فعلي ناجح يُرجِع JSON صالح للتحليل (لا نصاً حراً غير مُهيكَل)
🔹 دليل الإثبات: 3 استدعاءات تجريبية فعلية بأمثلة مختلفة: (1) إعلان طبيعي واضح، (2) إعلان بسعر شاذ جداً عن القسم، (3) إعلان بنص يحتوي كلمات نصب واضحة — والناتج الكامل لكل استدعاء
🔹 فحصك المباشر: قراءة الناتج الثلاثة بنفسك — هل المثال الطبيعي صُنِّف low فعلاً؟ هل المثالان الآخران صُنِّفا medium/high بسبب منطقي مكتوب بوضوح؟
🔹 عند الفشل: لا تنتقل للقطعة 2 قبل أن تثق فعلياً أن التصنيف منطقي على الأقل في الحالات الواضحة الثلاث
```

### 1.2 معالجة فشل الاستدعاء (Claude API غير متاح/بطيء)
```
🔹 النوع: كود
🔹 المدخلات: لا شيء — حالة افتراضية يجب تغطيتها
🔹 داخل النطاق: ماذا يحدث إن فشل استدعاء Claude API أو تجاوز مهلة زمنية معقولة (مقترَح: 10 ثوانٍ)؟
🔹 المُخرَج المطلوب: **قرار صريح مطلوب الآن:** عند الفشل، يُصنَّف الإعلان تلقائياً بمستوى `medium` (وليس `low` — لا نمنح الإعلان ثقة افتراضية عند غياب الفحص، ولا نوقف النشر بالكامل بسبب عطل خارجي مؤقت)
🔹 دليل الإثبات: محاكاة فشل عمدي (مثل قطع الاتصال بـ Claude API مؤقتاً أو استخدام مفتاح خاطئ عمداً للاختبار) ومراقبة الناتج
🔹 فحصك المباشر: التأكد أن فشل الـ AI لا يمنع إنشاء الإعلان بالكامل — فقط يصنّفه medium لمراجعة بشرية إضافية
```

## 🧩 القطعة 2 — Edge Function: `create-ad` (المعاملة الآمنة — أخطر قطعة في كل السبرنت)

### 2.1 منطق المعاملة الأساسي (بدون idempotency بعد)
```
🔹 النوع: كود
🔹 المدخلات: DraftAd كامل من Flutter (كل الحقول من السبرنتات 1 و2) + ai_risk_level/ai_review_notes من القطعة 1
🔹 داخل النطاق: إدراج صف في ads (status=pending) + ad_field_values + ad_images، كلها في معاملة قاعدة بيانات واحدة (Transaction) من جانب الخادم
🔹 خارج النطاق: ⚠️ صفر منطق idempotency في هذه الخطوة بعد — مهمة منفصلة تالية، لتفادي تعقيد خطوتين مختلفتين معاً
🔹 المُخرَج المطلوب: نجاح كامل يُرجِع ad_id، أو فشل كامل بدون أي صف مكتوب جزئياً
🔹 دليل الإثبات: استدعاء تجريبي ناجح + استعلام SQL يدوي بعده يُظهر الصفوف الثلاثة (ads/ad_field_values/ad_images) مرتبطة بنفس ad_id
🔹 فحصك المباشر: التحقق المباشر من قاعدة البيانات (لا الثقة بناتج الـ API وحده) أن كل الصفوف موجودة فعلاً ومترابطة بشكل صحيح
```

### 2.2 اختبار الفشل الجزئي عمداً (الأهم في كل القطعة)
```
🔹 النوع: كود
🔹 المدخلات: ناتج 2.1
🔹 داخل النطاق: محاكاة فشل متعمَّد في منتصف العملية (مثال: تمرير بيانات صورة غير صالحة عمداً تُسبِّب خطأ بعد نجاح إدراج صف ads)
🔹 المُخرَج المطلوب: لا يُترَك أي صف "يتيم" في ads بدون صور أو حقول مرتبطة بعد الفشل المتعمَّد
🔹 دليل الإثبات: استعلام SQL يدوي بعد كل محاولة فاشلة عمداً يُظهر صفر صفوف جديدة في ads
🔹 فحصك المباشر: هذا هو **الفحص الأهم في كل السبرنت** — لو وجدت ولو صفاً واحداً ناقصاً في ads بعد فشل متعمَّد، المعاملة غير آمنة فعلياً ويجب إعادة بناء منطقها قبل أي خطوة تالية مهما بدا باقي العمل جاهزاً
```

### 2.3 حماية التكرار (Idempotency بواسطة temp_draft_id)
```
🔹 النوع: كود
🔹 المدخلات: temp_draft_id من DraftAd (نفس المعرّف المُستخدَم في مسارات رفع الصور من السبرنت 2)
🔹 داخل النطاق: قبل أي إدراج، التحقق من عدم وجود إعلان مرتبط بنفس temp_draft_id مسبقاً
🔹 المُخرَج المطلوب: إرسال نفس temp_draft_id مرتين يُرجِع نفس ad_id الموجود فعلاً، لا إعلاناً مكرَّراً
🔹 دليل الإثبات: استدعاءان متتاليان فعليان بنفس temp_draft_id + ناتج كل منهما
🔹 فحصك المباشر: مقارنة ad_id من الاستدعاء الأول والثاني بنفسك — يجب أن يكونا متطابقين تماماً
```

## 🧩 القطعة 3 — ربط Flutter بـ `create-ad`

### 3.1 ربط زر "نشر" بالاستدعاء الواحد
```
🔹 النوع: كود
🔹 المدخلات: ناتج القطعة 2 الكاملة
🔹 داخل النطاق: زر النشر في Ad Preview Screen يستدعي create-ad فقط، استدعاء واحد، لا استدعاءات متفرّقة لكل جدول
🔹 خارج النطاق: ⚠️ تحقق صريح بنفسك أنه لا يوجد أي استدعاء مباشر من Flutter لجداول ads/ad_field_values/ad_images عبر PostgREST في هذه الشاشة — كل شيء يمر عبر create-ad فقط
🔹 المُخرَج المطلوب: زر النشر يتعطَّل فوراً عند الضغط (منع إرسال مزدوج)
🔹 دليل الإثبات: بحث نصي في ملف الشاشة عن أي استدعاء مباشر لجداول الإعلانات خارج create-ad
🔹 فحصك المباشر: قراءة نتيجة البحث بنفسك — صفر نتائج مطلوب
```

### 3.2 معالجة انقطاع الشبكة أثناء الإرسال
```
🔹 النوع: كود
🔹 المدخلات: القرار من موجز "المهمة ز": عدم مسح DraftAd عند الفشل، السماح بإعادة المحاولة
🔹 داخل النطاق: في حال فشل الاستدعاء (انقطاع شبكة)، DraftAd يبقى كما هو، رسالة خطأ واضحة، زر "إعادة المحاولة" يستدعي create-ad بنفس temp_draft_id
🔹 دليل الإثبات: تجربة فعلية — قطع الاتصال يدوياً فور الضغط على نشر، ثم استعادة الاتصال والضغط على إعادة المحاولة
🔹 فحصك المباشر: التأكد أن المحاولة الثانية تنجح وتُرجِع نفس الإعلان (بفضل idempotency من 2.3)، لا إعلاناً مكرَّراً ولا فقداناً للبيانات المُدخَلة
```

## 🧩 القطعة 4 — Ad Success Screen

### 4.1 الشاشة الأساسية + رسوم Lottie
```
🔹 النوع: كود
🔹 داخل النطاق: شاشة نجاح بألوان الهوية البصرية (فيروز/ذهبي) + رسوم Lottie
🔹 دليل الإثبات: لقطة وصف بصري للشاشة
```

### 4.2 زر "مشاهدة الإعلان" — جلب فعلي من قاعدة البيانات
```
🔹 النوع: كود
🔹 المدخلات: ad_id المُرجَع من create-ad
🔹 داخل النطاق: ⚠️ يجب أن يفتح Ad Detail Screen بجلب فعلي من قاعدة البيانات بـ ad_id، وليس من بيانات DraftAd المحلية
🔹 المُخرَج المطلوب: عرض الإعلان كما هو مخزَّن فعلياً، لا كما كان في الذاكرة المحلية
🔹 دليل الإثبات: تجربة فعلية بعد إغلاق التطبيق وإعادة فتحه ثم محاولة الوصول لنفس الإعلان من مكان آخر (مثل My Ads Screen) للتأكد أن البيانات استُمرَّت بشكل صحيح ومستقل عن الذاكرة المحلية
🔹 فحصك المباشر: هذا الفحص يكشف لو الوكيل "غشّ" واستخدم DraftAd المحلي بدل الجلب الفعلي — افحصه بنفسك تحديداً
```

### 4.3 زر "نشر إعلان آخر" + reset() نظيف
```
🔹 النوع: كود
🔹 داخل النطاق: استدعاء reset() من Provider (مبني في السبرنت 1) + العودة لبداية الـ Wizard
🔹 فحصك المباشر: بدء إعلان جديد بعدها والتأكد أن صفر أثر من الإعلان السابق (لا صور قديمة، لا قسم محفوظ)
```

```
🔹 النوع: كود
```

## 🧩 القطعة 6 — الانحدار الكامل وإغلاق المرحلة 9

### 6.1 اختبار شامل لكل السبرنتات الأربعة معاً
```
🔹 النوع: كود (تشغيل أوامر)
🔹 المُخرَج المطلوب: صفر فشل عبر كل ما بُني منذ السبرنت 0
🔹 دليل الإثبات: الناتج الكامل لـ flutter test وflutter analyze
```

### 6.2 رحلة "نشر إعلان كامل" من البداية للنهاية — الاختبار النهائي الحاسم
```
🔹 النوع: اختبار يدوي شامل
🔹 المدخلات: رحلة 2 الكاملة من خطة الاختبارات (8 خطوات، شاملة محاكاة انقطاع الشبكة وتكرار temp_draft_id)
🔹 فحصك المباشر — كل البنود التالية يدوياً وبالترتيب:
   ☐ اختيار قسم → تعبئة حقول → رفع صور → تحديد موقع → معاينة مطابقة فعلياً → نشر
   ☐ قطع الاتصال فور الضغط على نشر → لا صف ناقص في قاعدة البيانات (فحص مباشر)
   ☐ إعادة المحاولة بعد استعادة الاتصال → نفس الإعلان، لا تكرار
   ☐ فحص قاعدة البيانات → ai_risk_level وai_review_notes محسوبتان فعلياً بقيم منطقية
   ☐ "مشاهدة الإعلان" يعرض بيانات حقيقية مجلوبة من قاعدة البيانات
```

## ✅ معيار اكتمال السبرنت 3 — معلم رئيسي 🎯

عند اكتمال كل الصناديق، **المرحلة 9 (Post Ad Wizard) مكتملة بالكامل**، وأول إعلان حقيقي منشور فعلياً على Staging من البداية للنهاية. هذه أهم نقطة تحقق وصلت لها المنصة حتى الآن — بدونها لا توجد منصة قابلة للاختبار مع مستخدمين حقيقيين.

الخطوة التالية هي السبرنت 4 (طبقة الثقة: Verification Screen + My Reviews Screen + trust_score). قولي لما تخلص وتختبر السبرنت ده، وهجهّزلك دليله الذرّي.
