## 🧩 القطعة 1 — `create-payment` Edge Function

### 1.1 التحقق من صلاحية الطالب أولاً (قبل Paymob)
```
🔹 النوع: كود
🔹 المدخلات: مفاتيح Paymob Sandbox من Supabase Secrets
🔹 داخل النطاق:
   - التحقق أن المُستدعي مستخدم مسجَّل فعلاً (auth.uid() موجود وصالح)
   - التحقق أن الإعلان المطلوب تعزيزه يخص هذا المستخدم تحديداً
   - إدراج صف في جدول transactions بحالة pending قبل أي استدعاء لـ Paymob
🔹 خارج النطاق: استدعاء Paymob في هذه الخطوة بعد
🔹 دليل الإثبات: استدعاء بـ user_id صحيح لكن إعلان لا يملكه → رفض صريح مع كود خطأ واضح
🔹 فحصك المباشر: تجربة الاستدعاء بمستخدم تجريبي لا يملك الإعلان عبر Postman → رفض، لا معاملة مفتوحة
```

### 1.2 استدعاء Paymob والحصول على iframe_url
```
🔹 النوع: كود
🔹 المدخلات: وثائق Paymob Sandbox — التسلسل الرباعي:
   (1) authentication_token ← (2) order_id ← (3) payment_key ← (4) iframe_url
🔹 داخل النطاق: تنفيذ التسلسل كاملاً + تخزين order_id في صف transactions من الخطوة 1.1
🔹 خارج النطاق: ⚠️ مفاتيح Paymob لا تُمرَّر للعميل أبداً — iframe_url فقط يُرجَع
🔹 دليل الإثبات: iframe_url فعلي من Paymob Sandbox + فتحه في المتصفح يُظهر صفحة دفع حقيقية
🔹 فحصك المباشر: فتح الرابط بنفسك في المتصفح — صفحة دفع Sandbox حقيقية، لا خطأ أو رابط وهمي
🔹 عند الفشل: توثيق الخطوة المحددة من الأربع التي فشلت (1/2/3/4) لا "Paymob لا يعمل" كوصف عام
```

### 1.3 تحديث transactions بكل معرّفات Paymob
```
🔹 النوع: كود
🔹 داخل النطاق: ربط order_id وpayment_key بصف transactions قبل إرجاع iframe_url للعميل
🔹 دليل الإثبات: استعلام مباشر على جدول transactions بعد استدعاء ناجح → الصف يحتوي order_id وpayment_key فعلاً
🔹 فحصك المباشر: فحص الصف مباشرة من لوحة Supabase
```

## 🧩 القطعة 2 — `payment-webhook` (الأهم والأخطر في كل السبرنت)

### 2.1 التحقق من HMAC — لا شيء قبله أبداً
```
🔹 النوع: كود
🔹 المدخلات: ترتيب حقول HMAC الموثَّق من وثائق Paymob (المحفوظ في السبرنت 5 كمرجع)
🔹 داخل النطاق: حساب HMAC-SHA512 بالترتيب الحرفي الدقيق، مقارنته بـ hmac الوارد في الطلب
🔹 خارج النطاق: ⚠️ لا تُعالَج أي بيانات من محتوى الطلب قبل نجاح التحقق — صفر استثناء
🔹 دليل الإثبات (مزدوج — كلاهما إلزامي):
   أ) HMAC صحيح → قبول ومعالجة
   ب) HMAC خاطئ عمداً (تغيير حرف واحد فقط) → 401 فوري
🔹 فحصك المباشر: تنفيذ الاختبار (ب) بنفسك عبر Postman وقراءة الكود المُرجَع → 401 لا 200 أو 500
🔹 عند الفشل: أي منطق معالجة وُجد قبل HMAC هو ثغرة أمنية حرجة تُصحَّح فوراً قبل أي خطوة تالية
```

### 2.2 Idempotency — منع التفعيل المزدوج
```
🔹 النوع: كود
🔹 داخل النطاق: قبل أي معالجة، فحص حالة transactions بـ order_id الوارد:
   - completed → إرجاع 200 فوري بدون أي معالجة
   - pending → تابع
🔹 دليل الإثبات: إرسال نفس محتوى Webhook مرتين متتاليتين
🔹 فحصك المباشر: عدّ صفوف is_boosted = true للإعلان التجريبي → يجب أن يبقى 1 لا 2
```

### 2.3 ترتيب المنطق الداخلي (غير قابل للتفاوض)
```
🔹 النوع: كود
🔹 المُخرَج المطلوب: الترتيب الحرفي في الكود:
   HMAC أولاً ← Idempotency ثانياً ← تحديث transactions ← استدعاء التفعيل
🔹 دليل الإثبات: محتوى ملف الدالة كاملاً
🔹 فحصك المباشر: قراءة الكود بعينك والتأكد من الترتيب قبل أي اختبار فعلي — هذا الترتيب هو خط الدفاع الأول
```

### 2.4 اختبار Sandbox من البداية للنهاية
```
🔹 النوع: اختبار متكامل
🔹 الخطوات المطلوب توثيقها كلها:
   1. استدعاء create-payment → iframe_url
   2. إكمال دفع ببطاقة Sandbox التجريبية من وثائق Paymob
   3. استقبال Webhook الفعلي من Paymob
   4. تحديث transactions إلى completed تلقائياً
   5. تفعيل is_boosted أو الاشتراك تلقائياً
🔹 فحصك المباشر: فحص الخطوتين 4 و5 مباشرة من لوحة Supabase بنفسك
```
